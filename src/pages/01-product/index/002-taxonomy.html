2The task taxonomy

Task types are the unit at which the product is measured: verdict rates and the nudge schedule are set per task type. A task type is a vertical plus a shape of plan: where the point of no return sits, which step classes the plan needs, and what the envelope must contain.

Phone work covers only non-authenticating calls: bookings, chasing, enquiries, availability and appointment setting. A call never carries a value from the vault, in either direction (DR-021), so a step that needs an identity value verified by voice moves to an online surface where the substitution component can place it, or it bounces to the user's own device.

Reversibility belongs to a step, not to a task, so Table 1.1 names the step that carries the point of no return in each type: the one dual-controlled or bounced. The test is applied as written: an act a third party must undo is irreversible even where it would undo it on request; only an undo by our own action at no cost, by an act the envelope admits, counts, and a step the classifier cannot decide is treated as irreversible (the classifier in 02).

Two names, two owners. This page holds task types and nothing smaller. A task type is identified as market, vertical and name, lower-case with hyphens, IN/health/book-appointment, and the same shape in another market is another task type, because its rails, its flags and its timers differ. The unit below it, the step type, lives in the step-type catalogue that 02 owns: its schema is core, its entries per market ship in the legal pack, and each entry carries the step type's act type, its defaults and its allowances in the columns 02 fixes. A plan is a list of step types drawn from the catalogue, written IN/health/book-appointment-by-phone, so the planner's templates in 02 and the routing to a pool in 04 key on the catalogue's step type and never on Table 1.1; the catalogue is the only place step types are enumerated.

The timer table is keyed by task type and is product's to fill; every value in it is illustrative until the pilot sets it. Per task type it holds the planning deadline, counted from received; the default step deadline, which a catalogue entry may shorten for its step type; the nudge schedule, a list of offsets from the moment a wait began and then lapse, one list each for awaiting-authority, awaiting-user and awaiting-verdict; and the default response window for a third party, which the catalogue entry for the party's step type may override. The task service reads it on every transition; a person never sets a timer by hand (the state machine in 02).

Everyday tasks, the errands and bookings below the line the thesis draws, are in scope from the first day and are most of the volume (DR-020). They are not a vertical of their own and they do not have their own harness: they run on the same envelope and the same classifier, which finds most of their steps reversible and so runs them as ai steps with no worker and no dual control. Table 1.1 holds the task types whose point of no return has to be named, which is why the everyday shapes are not in it; a market's legal pack governs identity and institutional acts, not a table booking, so nothing in this section waits on a pack.
