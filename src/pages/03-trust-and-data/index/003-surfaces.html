3Execution surfaces

Boundary four is the surface, the one boundary a value must cross, because the institution on the far side needs the value itself. Ownership makes it safe: every surface is ours, a worker never uses their own browser, phone or mailbox, and each surface renders the value as dots or an alias on its human side while its institution side receives it, and the call is not one of them: a value never reaches a call at all (DR-021, 3.2). The component view of the same three surfaces is in 02; this section is the specification of the human side. Two configuration sets it reads are this page's and not the step-type catalogue's, whose columns 02 fixes: the surface settings per market (the browser stream's delay line and the maskers' format set from Table 3.1) and the party register per market (for each contactable party, its declared web domains and their certificates, the numbers we dial, its mail domain, the keys of its voice menu that navigate and the keys that commit, from which a step's catalogue entry takes its menu map (02, Table 2.6), beside it a page map per page naming the controls that navigate, every other control being committing (3.1), and a mask map for each page a step may reach, naming the regions and fields the masker may deliver as text and, for a page marked as an authenticated portal, the whitelist of fields a step may read). Both are read by the controllers and the maskers at run time, versioned and signed with the market's legal pack, and changed only as a recorded change; a page with no mask map clears nothing (3.1).

3.1The managed browser

For a workflow the library has modelled, what a worker is given is not the page but a structured task card derived from it, and the substitution component places the values at submit as it does anywhere else (DR-022). Masking is then a property of the data the card carries and is deterministic. The streamed page and the five masks below are the fallback for a counterparty the library has not modelled, deferred until volume justifies the build, so the paragraphs that follow specify a mechanism the pilot does not use.

The browser runs in our sandbox in the market's region, one session per task, and the worker never runs it: the console shows a pixel stream of the session and forwards clicks, scrolling and keystrokes into ordinary fields, and the browser controller admits each forwarded click by one rule: a click is a committing action unless the page map the party register carries for that page names the control as navigation. Following a link inside the party's declared domains, scrolling, focusing a field and typing non-sensitive text are navigation by default; a button, a form submit or any scripted control is committing unless the page map names it, and needs the approval token and the window-and-version check like a submit; on a reversible step the controller refuses every click outside the navigation map and every submit, so a control that commits by script on a page reached inside a reversible step cannot fire from a worker's click or the ai executor's (02, 4.5). The worker holds no document, no cookie, no download and no clipboard. When the task card reaches a field that needs a value, it offers one action, "place {{pan}}", and nothing to type. The tap goes from the console to the task service, which hands it to the browser controller, the controller to the substitutor, and the substitutor's privileged driver session, attached to the same browser over a channel the worker's client does not have, focuses the field the descriptor names, types the value with synthesised input events so the site's own validation runs, and reports the field's rectangle to the stream compositor, which paints it as dots from focus until the field is cleared or the page navigates, following it through scrolling because the driver re-reports on every frame. Autofill, form history, extensions and the driver's read-back of field values are disabled in the session.

Every frame passes a masker before the worker sees it, and the stream runs behind the live page by a fixed delay line set so the masker always finishes first (a few seconds; illustrative, an entry per market in the surface settings). The masker works on the document's text and accessibility tree, never on pixels, and applies five stream masks in a fixed order. Coordinate masks: the rectangle of every placement record, painted from focus until the field is cleared or the page navigates. Field-type masks: every field whose declared kind is password, and every field whose label or accessibility name matches a class name in Table 3.1, painted from the first frame whatever it holds. Digest masks: every candidate window of the text layer, digested through the hash service against the keyed digest set (1.2), with each match's layout box painted. Format masks: every text run on every page, not only after a submit, is matched against the class formats of Table 3.1, the identifier patterns, dates in every order, card and account shapes, currency amounts in the written form of the financial-fact class, a name, the user's or any people node's in the context store, as whole tokens in any field or region, and any name-shaped run in a field the party register marks as an identity field (1.1), the reference shapes the register records for the party, and the health and legal term dictionary of 1.2, and a run that matches is painted, so a value in no known form is covered by its form. Region masks: image and canvas regions painted whole unless the mask map clears them. The same replacement runs over the document object at every capture point, so a DOM capture never holds a value. When a confirmation page repeats the value the region is painted, the panel reads "the page repeats {{pan}} (masked)", the model runtime receives the masked text layer, and the ledger writes the echo and its masking. On any page reached by a submit that used a placement the masker also covers, by shape, every digit run longer than a threshold (illustrative: six) until the page changes, so an echo the matcher cannot read is covered by shape rather than by recognition. What may be delivered as text is decided by the step's mask map, the party register's list of the regions and fields cleared for delivery on that page: a party's default map clears headings, labels, navigation and button text by their accessibility roles and nothing else, a page's map adds the fields the step needs to read, and on a page the register marks as an authenticated portal there is no default: every text run and every figure is painted except the fields the map whitelists as needed for the step's outcome, so balances, history and other people's identifiers that were never vaulted are dots to everyone, and a portal page with no whitelist has no stream to a person and is never a human step: it is ai where the conditions of 02, 3.1 hold, the party marked machine-navigable for the step type, a verifier the harness can run and a surface the scope block opens to ai, and otherwise it bounces to the user as a user step. A frame is delivered only when every text run and every image region on it is accounted for: matched by digest or by format, painted by coordinate or field type, covered by shape, or cleared by the step's mask map. A run the masker can neither match nor clear is painted by default and the frame is held for re-masking: it is not delivered, the stream shows the hold screen with a reason, the frame is re-masked with the default paint and wider shape masks and re-checked by the verifier of 4.1 before it can leave, and the step pauses, still running with the surface held and its timer live. There is no residual of plain text below a threshold: a run that matches nothing and that no map clears is painted, never delivered. That is the fail-closed default: over-masking costs a worker a moment; a frame the masker cannot clear does not leave the pipeline, so the camera and the two-person zone in 04 record a failure of this mechanism and are never its closure. If the masker cannot confirm a frame is clean for any other reason, because the hash service is unreachable or the frame missed the delay, the same hold applies. A hold changes no step's class: an ai step has no stream to a person and continues on the driver unaffected; a human step waits, and if the hold outlasts a bounded wait (illustrative: one minute) the task service closes it on the tick: failed-retryable, re-queued on the same route so another worker takes the card once the masker is clear, where no fired marker exists, and failed-final with the marker as its evidence where one does, a submit already issued behind the held frame, the re-plan then issuing a status enquiry before any repeat (2.1); the console's possible-exposure control closes a step the same way, retryable without a marker and final with one; a human step that reaches a page with no mask map holds the same way, and the re-plan runs it as ai where those conditions hold, bounces it to the user as a user step otherwise, or the party register gains a map as a recorded change. Every held frame writes the line "A frame was held until it could be masked; no person saw it", an echo-masked event in its held form (8.1). The capture at submit and response is the same masked frame and a document snapshot with the same masks and the same whitelist applied, so QA, a checker and the worker see the same fields and nothing else (4.1). Where a step needs an amount for its outcome, a quoted fee against the sub-cap or a slot's price, the catalogue entry names that one amount field, the controller compares the amount the masker painted with the envelope's cap line, and the panel shows only the comparison, "fee inside the sub-cap: yes", never the amount; a step whose script cannot decide from the comparison closes blocked-needs-user with the amount held as an alias for the user's device. Where a check needs a party-issued reference confirmed, the council's reference against the filled form in the legal journey of 01, the browser controller's field-match check asks the hash service whether the field's digest equals the digest behind {{reference.council}} and the check panel reads "reference matches the notice: yes", so the checker confirms the reference while it stays dots.

3.2Telephony

We place the call from our numbers on our carrier; the worker is on one leg and the institution on the other, and the worker speaks and listens in the ordinary way. Nothing from the vault goes onto a call, in either direction: the substitution component has no media function, the worker's leg is never muted, there is no delay line, no streaming transcriber in the live path and no re-voicing (DR-021). A script step that would have read "state {{dob}}" does not exist on this surface; a step that needs a value stated or verified by voice is placed on the browser or the relay instead, or it is a user step and bounces to the user's own device.

The claim this surface supports is therefore narrower, and it is the claim the trust story now makes: no person who works for us ever sees or hears a value from the vault, and no task is handled in a channel where a value would appear. Phone work is scoped to non-authenticating calls, bookings, chasing, enquiries, availability and appointment setting, so no desk has a reason to state a value and no script asks for one. What makes a call non-authenticating is now a test rather than a category: the desk asks for identity to map to an account, not to unlock one, and the party register carries which it is (DR-026). A mapping key overheard cannot be used to become anyone; a credential can, which is the distinction the scope rests on. What a worker does hear is the far party using the user's name and the details of the thing being booked, which is a fact about the user rather than a value, and is bounded by the need-to-know card, the vetting and site controls of 04 and the ledger rather than by a mechanism in the media path.

A far party that states a value unasked is an exposure, not a path the design offers: the worker closes the step with the possible-exposure control, an incident opens, the pipeline's pass over the recording tokenises the span and the ledger records it as an exposure with its incident reference. The recording still reaches the evidence pipeline in region, where the redaction and verification of section 4 apply unchanged, and the carrier carries audio that contains no vaulted value and stores none of it, provider-side recording, transcription and voicemail being disabled by contract and by configuration, which is a lighter requirement on the carrier than the previous edition's and is the one the vendor evaluation in 07 now tests.

3.3The mail relay

Outbound mail is composed with aliases, by the worker in the console or by the AI, from the user's own address: sent through the user's provider under the mailbox's send scope where the user has granted it, or pasted and sent by the user from a draft the harness wrote where they have not, as DR-018 fixes; no message to a third party leaves from an address of ours, and the task's relay address at our domain is inbound only, for the user's forwards. The basis for a message in the user's name is the one the last row of Table 3.5 records for a call, and a jurisdiction's disclosure rule is that row's flag. The relay releases a message only if it instantiates the step's catalogue template, fixed sentences with named slots typed non-committing, or the step holds an approval token naming the hash of the message as checked; a message that matches no template is a committing action and needs the token, and on a reversible step, which holds none, the relay releases template instances only, so free-composed text cannot commit the user through the relay (02, 4.3). On send the relay, as the surface controller, sends the substitutor a placement request naming the message and the occurrences, with the signed step context; the substitutor rewrites them in the relay's outbound store through the relay's injection endpoint, writes the line, and the relay delivers. That outbound store is the one place a value rests outside a field or a call leg, and it is built not to rest: memory only, inside the real-value zone, on an instance with no persistent volume and no swap, encrypted under a key held by the relay's workload identity and released to nothing else, and bounded by the placement window. A receiving server that has not accepted the message inside the window, because it defers or greylists, gets nothing further: the body is dropped, the line closes "not confirmed", the step closes failed-retryable with a retry token, and the next attempt is a fresh composition and a fresh placement. The relay keeps no sent copy. The evidence copy is the alias draft and the delivery receipt, and the console keeps no history a worker can open, so nothing anyone can re-open holds a value. A worker's own mailbox is never a route. A reply lands in the user's own inbox and reaches us by the mailbox's read connector, or by the user's forward to the task's relay address; the user's mailbox is a route only through that connector and the proxy, and either way the mail terminates at the vault's edge proxy like any other channel, with the digest set added: known values, our own value quoted back included, become their aliases, new values become new aliases with a "received" line, an amount, a balance or a fee in the body becomes a financial-fact alias by the amount pattern of 1.2, attachments become document aliases, and only then does the tokenised message reach the relay's renderer or the planner. The console never shows the tokenised message as it stands: the relay's renderer applies an allowlist, which this section defines and the evidence pipeline of 4.1 reuses, and paints by default every token outside the cleared vocabulary, the language's common lexicon, the party register's terms for that party, the catalogue entry's expected phrases and numbers below the digit-run threshold, so an out-of-lexicon token, a proper noun that is not a cleared term, a digit run or a match to any class format is painted whether or not the four detectors named it, and the worker reads the painted rendering; a painted token the worker needs is requested from the party as a typed field on the task's thread, where it is tokenised on arrival, or the step closes blocked-needs-user. The planner receives the tokenised message, screened again by the model runtime's detector. Behind the proxy's detectors, the renderer's default paint is the second line for what a person reads, as the browser's default paint is for a frame (3.1) and the transcriber's allowlist for a call, and the console's card renderer applies the same paint to every free-text field of a task card after the hash service's screen (Table 3.6, path 4).

The incident queue these rows and 4.1 open onto is one record type with one owner. A record carries an id; a kind from a fixed list (station integrity, value demanded, worker request, frame held past its wait, verifier hit, screening hit, reconciliation mismatch, rate-limit breach, region outage); the task and step ids; the alias; the rule, check or component that raised it; the time; an owner; and a state, open, owned or closed with one of three findings: no exposure; exposure to a category of person, which writes the user's ledger line; or a defect fixed. The QA and escalation function on shift owns it, as 04 sets out: every record is owned before the shift ends and closed within the period the market's legal pack sets for breach assessment to-verify. It is not the exceptions board, which is the watchdog's view of timers and holds no incident, and it is not the ledger, which records what touched the user's data: an incident writes a ledger line only where a value was exposed, withheld or destroyed.
