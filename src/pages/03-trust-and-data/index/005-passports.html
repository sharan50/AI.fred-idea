5The passports

A passport is how a value or an authority the user already holds reaches a task without passing through a person: a universal device bounce-back, and per market an adapter to the rails that release documents, financial data and payment authority under the user's own consent. Every rail below is gated to the named user and to an approved counterparty, so the adapter reaches a rail through the user's own session or a regulated partner and never around them, and whatever a rail returns terminates at the vault's edge proxy in front of the adapter (1.2). The interface every adapter implements is in 02; what each rail permits a delegate to do is recorded here as it stood in the research notes of this edition, with the design intent stated where the notes did not reach. Nothing in this section moves the capability ceiling; it records the current state the flags in section 6 respond to.

5.1The universal device bounce-back

Every market shares one passport that needs no rail: the user's bound device. A user step bounces there in one of the four forms the classifier in 02 fixes, approval, user act, one-time code and do-this-yourself, and the device's signed response closes it. The first is a one-tap approval, which is always an envelope confirmation or a device-signed extension. Every envelope line carries a scope, task-wide or one step by its id: a one-tap approval of a step's request produces a new version carrying a step-scoped line; a one-tap approval of a task-level request the task service raises, the validity-window renewal, produces a task-wide line; and a user's own edit produces a task-wide line. Nothing we perform runs on the tap alone; classification re-runs for every step on the new version, and a step-scoped line admits only its step, so that step is re-classified as inside the envelope and fires under dual control while no other step gains from the line, whereas a task-wide line is read by every step the re-plan re-issues (01, 4.2; 02). The other three are acts the user performs on their own device. A user act is done in the institution's own app or session: a biometric or face check, a UPI PIN, a bank-app approval, an e-signature ceremony, a consent screen (DigiLocker, Account Aggregator, Open Banking, a government login), with our script on the device and a callback to the task. A one-time code is entered by the user on their own device and by nobody on our side, and where the institution's flow allows it the user enters it in the institution's own app or page on that device, so nothing passes through us at all. Where the code must land in a field on our surface, it travels on a one-shot channel: the browser controller or the telephony controller opens the channel for exactly one step, encrypted end to end to the surface driver's key so every process between the device and the driver carries ciphertext, and closes it on first use or when the code expires, whichever is first (the institution's own validity; illustrative: a few minutes). The driver places the code under a placement record like any other placement, so the compositor paints the field by coordinate before the first character lands and the driver's read-back stays disabled; a one-time code is never carried on a call at all, because the channel carries no value, so a step that needs one placed is a browser step or it bounces to the user. The code touches no vault, no model, no console and no log, and the substitutor is not involved because there is nothing to detokenise. The ledger line is "You entered a one-time code yourself, on your device; the worker saw the field as dots", and Table 3.6 carries the path as 23. {{otp}} is never an alias because the code is never ours to hold, and a code read aloud to a call in progress is an exposure and not a placement, closed with the possible-exposure control rather than by a buffer that no longer exists (3.2). And a "do this yourself" step hands the user a precise instruction when a jurisdiction reserves the act to them, shown at plan time as "you will do this yourself", never as a box to tick (the envelope in 01). The ledger writes each as "you did this yourself, on your device", and no worker is present for any of them.

5.2India Stack: DigiLocker, Account Aggregator, UPI Autopay

Each Indian rail is gated the same way: the user authorises in their own session and only an approved or regulated counterparty may hold the door. Table 3.4 carries each claim with its status; this paragraph states the design that follows. DigiLocker's requester model is the shape we want everywhere: consent on a DigiLocker page that shows the purpose, then a pull that reaches our adapter, through the vault's edge proxy, as {{doc.pan-card}}. Account Aggregator data is pulled by a regulated financial information user, so we sit in front of one as a customer interface partner rather than pretending to be one, and the consent artefact stays the user's to revoke. Aadhaar authentication is never ours to perform: the user's face or OTP check is a bounce into the institution's own app, and {{aadhaar}} follows the one rule in 1.1: held in the vault as received, never placed in full, with the vault-issued {{aadhaar.last4}} the only form a surface receives. Payment authority is where the ceiling and the rail differ most: the authentication directions require a factor unique to each transaction, so a payment under the cap is the user's own act on their device today and the flag reads bounce, with the ai dual-control form held in reserve for a rail that admits a registered agent. The KYC last mile is the same story: we fill the form and the user performs the identification.

5.3United Kingdom: Open Banking and the current identity rails

The UK's data rails are mid-transition and its identity rails are consolidating, and the research for this edition read none of it at source, so every UK claim is to-verify and sits in Table 3.4: the Future Entity succeeding Open Banking Limited, the commercial variable recurring payment scheme, One Login and the trust framework, and the three documents on agents. The question that decides our adapter, whether a party acting for the customer can hold an account-information or payment-initiation consent or whether we read through a regulated provider under the user's own strong customer authentication, was not reached and is an open legal item with its primary sources named in 07 to-verify. Design intent: consent is always the user's, given in their bank's own app; the resulting token lives in the vault and is injected into the adapter's calls by the vault's edge proxy; a variable recurring payment mandate set up by the user is the rail on which a delegated debit under the cap may read delegated, which is the condition on the UK line of Table 3.5; the debit itself is a placement under 2.1, the instruction under the mandate obtained from the adapter and placed by the substitutor, and the rail's binding is a second layer, never the closure. Identity is GOV.UK One Login and the Digital Verification Services trust framework; our adapter presents a wallet or certified-provider credential through the substitutor like any other document, and the login itself stays the user's act. The FCA's Mills Review, HM Treasury's payments consultation and the CMA's guidance on AI agents are the three documents the flag table's "what to ask" column will be argued against.

5.4United States: bank-data aggregation and card tokenisation

The research sprint did not reach the US rails, so this section is design intent with the current state chipped to-verify. Bank-data aggregation: the adapter reads account data through an aggregator under the user's own consent given in the bank's flow, with the aggregator's token held in the vault and injected into the adapter's calls by the vault's edge proxy, and emits aliases for identifiers and plain facts for the context store; the state of the consumer financial data-rights rule under section 1033 of the Dodd-Frank Act, and which aggregators operate under it, is the first item to check to-verify. Card tokenisation: a network token bound to this task and its cap stands in for {{card.primary}}, so a merchant never receives the card number and no card number is ever typed; the substitutor obtains the token from the adapter and places it like any other value under its ordered checks (2.1), the network's binding of the token to the task and its cap being a second layer and never the closure; the card networks' agent-payment programmes, which bind a tokenised credential to a named agent, a merchant scope and a consent policy, are the rail that lets the US flag for a payment under the cap read delegated on the token and bounce off it to-verify. Liability is the open question: Regulation E is reported to have no rule for a standing authorisation given to an agent to-verify, while California's AB 316, in force from 1 January 2026, bars a party that developed or used an AI from arguing that the AI autonomously caused the harm verified [5], which is one more reason the ledger names the party that placed every value. Identity in the US has no national rail; a document is what the user uploads or a state's mobile licence presents, and identification acts bounce.
