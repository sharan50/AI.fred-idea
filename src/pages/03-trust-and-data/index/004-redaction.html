4Artefact redaction

The evidence system is the fifth boundary and the one most easily forgotten: a screenshot, a recording or a transcript is a real value written down. So the pipeline lives inside the real-value zone, nothing raw leaves it, and it is designed as a leak path first and a record second. DR-009 fixes this; 02 places the pipeline among the components and draws it; this section is the redaction contract.

4.1Boundary five: capture, redact, verify, store

Capture takes browser frames and document snapshots before each submit and after each response, the raw audio of both call legs, the transcript, call metadata and the alias version of mail into the pipeline's memory only: nothing raw is written to disk, queued or logged, memory is not swapped, and an instance that crashes loses its material rather than dumping it. Each artefact carries the placement registry from the substitutor's receipts, which alias went into which field rectangle, which audio window, which message occurrences; the registry is the map the redactor works from, and an artefact without it is not accepted. Redaction applies five artefact masks in a fixed order: coordinate masks from every registry entry, with a margin, from the frame of placement to the frame of navigation; known-value masks by keyed digest over text layers, document captures and transcripts with spoken digits normalised; audio windows, every known value and every class-format match replaced with silence, the allowlist of 3.3 run over the pipeline's own batch transcript of the recording, and every span a worker flagged with the possible-exposure control of 3.2 masked with its incident reference, with a transcript marker naming the alias for a match and reading "span masked" for a withheld span. There is no live allowlist on a call and no placement to mask, because nothing from the vault reaches a call (DR-021); the stored recording therefore carries less than the headset did rather than no more, and the span no detector names and no worker flags is the residue 07 declares rather than a closure this section may claim; format masks on every frame, capture and transcript, any run or span matching a class format, the party's recorded reference shapes or the health and legal dictionary, with the shape rule's digit runs beyond the threshold after a submit that used a placement; and mask-map masks, every run and figure the step's mask map does not clear, which on an authenticated portal page is everything outside the whitelist. Aliases replace matches in transcripts and document captures, so a transcript reads {{dob}} where the value was. The output is the masked artefact and a redaction manifest stating, in aliases, what was masked by which rule.

Verification is a second pass by a separately built service with its own recogniser over the pixels, its own speech recogniser, its own normaliser and its own digest set: the hash service issues two digest sets under two keys, one to the maskers and one to the verifier, so the verifier derives nothing from the vault and holds no vault credential of any kind; it shares no code with the redactor, is owned by a different team and changes on a different schedule. It checks the mask map and the allowlist's windows as well as known values and formats: a run or figure outside the step's whitelist on a portal page, or outside the cleared regions on any page, is a hit, and so is an audible span of the stored audio, or a readable span of the stored transcript, that the allowlist of 3.3 would not have cleared when run over the pipeline's batch transcript. It fails closed. Any hit quarantines the artefact in memory: nothing is stored, an incident opens naming only the alias and the rule that missed, redaction re-runs from memory with wider masks, and after a small fixed number of attempts, or when the incident closes if that is sooner, the raw material is dropped and the step's evidence becomes a structured note, "evidence withheld: redaction could not be verified". The step keeps its outcome code, because artefacts attach for audit and dispute only and never for the outcome; the user's ledger records that the artefact was destroyed rather than kept. The store accepts an artefact only with the verifier's signature over its hash, so nothing can be written around the second pass, and the incident handler receives the manifest and the matched digest's id, never the artefact. Only a verified artefact is stored, encrypted, under the task and in the market's region, for the retention the market's legal pack sets to-verify; the ledger outlives it.

4.2Who may open what, and when

There is no raw store for anyone to be granted access to, so Table 3.3 is the whole access list, and every opening is itself a ledger event the user can read. No tier, L3 included, has a raw view; no debugging mode shows one; and the live masked stream a worker, or a dual-control checker, watches during a step is not stored and cannot be re-opened. The session log the console keeps per station, frame identifiers, timestamps, the station and the sign-in, which the site controls in 04 name beside the camera, is metadata about the stream and not a copy of it: it holds no frame and no value, so it sits outside Table 3.3 because it holds nothing to view. The room's camera footage is a site record and not an evidence artefact: it never enters the evidence pipeline, it records a room whose screens show only masked frames, it is kept by site security under the incident process for a fixed retention, and Table 3.3 does not list it because it holds nothing a task produced.
