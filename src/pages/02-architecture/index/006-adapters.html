6The market adapter model

One core is built once and knows no country; each market is added as a repeatable unit of three parts. The core is the planner, the classifier, the task cards, the alias vault and substitution, the authority envelopes, the state machine, verification, the worker console, the access ledger, the intake gateway and the policy layer's mechanism; the flag table that mechanism reads is the per-market half. The unit per country is a passport adapter, a legal pack and a shift. The harness that keeps a worker in Bengaluru from seeing a value is the same harness everywhere, so a new market never re-argues the trust design. The decision is DR-007; the playbook is the expansion playbook in 06.

6.1The adapter interface

An adapter implements one interface, the same for every market, and never holds a raw byte: it reaches its rail only through the vault's edge proxy, deployed in front of it, which terminates every rail response and tokenises it against a declared per-field schema before the adapter receives the payload, as the three doors in 03 specify; the adapter holds no vault SDK and has no network route to the vault, and the rail token it presents on each call lives in the vault and is injected by the proxy. Four operations: fetch a document (returns an alias and non-sensitive metadata such as type and issue date); fetch financial data under the user's consent (returns aliases for account identifiers and non-sensitive facts for the context store); manage a consent or mandate (create, inspect, revoke, always initiated by the user on their device); and present a document, an identity attribute or a payment instruction to a third party on a surface, through the substitution component like any other placement. A delegated debit under the cap is therefore a placement and never a path of its own: the substitutor obtains from the passport a task-bound token, scoped to this task, its cap and the named merchant, or a payment instruction under a mandate the user set up, and places it on the surface, so its ordered checks, the act, the window, the version, the party, the remaining cap and the dual-control token, and the controller's check at the committing action all apply. It is a committing placement (section 4.5), because the placement is itself the act the rail or the merchant executes: the substitutor requires the approval token for it like a submit and writes the step's fired marker before the first character is delivered, a not-confirmed receipt closes the step failed-final with the marker and the re-plan issues a status enquiry before any repeat, so one act never debits the user twice and the reservation stands against the cap, and a narrowing inside its placement window does not stop it, which the outcome report says; the rail's own binding of the token to the task and its cap is a second layer, the to-verify item the passports in 03 carry, never the closure. The device bounce-back is not an adapter; it is universal. The rails each adapter wraps are the brief's fixed list, drawn in Figure 2.3; what each permits a delegate to do is researched in the passports in 03. On UPI the adapter wraps the mandate rail for consents the user creates on their own device; a delegated debit under the cap is a bounce in India today, performed by the user's own device on UPI Circle or Reserve Pay, per the flag table, and the ai dual-control form is held in reserve for a rail that admits a registered agent.

6.2The legal pack and the shift

The legal pack holds four things the core reads at runtime and never hard-codes: the policy flag table, which the policy layer consults for every step, together with the scope block of section 3.1; the data-residency map, which says which component's data lives where and under what safeguard, the vault's regional hosting included; the refusal list, which the planner consults before any step executes, carrying the reason codes of what we refuse to do in 01 plus the market's own lines, a vertical not yet open among them, refused from received with the reason code refused-not-offered; and the step-type catalogue's entries for the market (section 3.3), both tables, whose schema is core and whose values per step type and per party are the market's. In form the pack is a directory of tables in a plain structured format with a manifest that names each table's schema version and row count, versioned as a whole, signed by two holders (the market's legal owner and the platform owner) before a pilot opens, and verified against the core's schema at load: a required row missing (a flag for every act type in Table 2.5 that consults one, a residency entry for every store, a timer row for every task type) fails the load; the act types Table 2.5 marks as consulting no flag, of which entering a one-time code is the one in this edition, need no row and are not a missing row, and the previous version stays in force. A new version is loaded on a signed reload without a restart and applies exactly as a flag flip does (section 2.2): it voids the context and the token of every step not yet fired, which is re-classified against the new version before it can run again, and a step whose placement request is already inside its placement window completes that placement under the version its context names, and nothing more. The shift is the operational third: a market is not live until a shift covers its waking hours from the office, per the shift design in 04. The residency map itself is the data-residency map in 03.
