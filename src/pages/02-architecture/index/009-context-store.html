9The context store

The context store lets the planner act without asking the user things they have already told us, and its design rule is that every fact says where it came from and how much to trust it. It is a temporal knowledge graph: nodes are the user, institutions, documents, people and places; edges are facts with validity intervals. A people node is a natural person other than the user, a nominee, a relative, a contact, and it carries aliases, never values: its name, date of birth, identifiers, contact details and address are aliases of the personal-fact class of Table 3.1 in 03 qualified by the person reference, {{name.nominee}}, {{dob.nominee}}, {{phone.mother}}, vaulted at the proxy like the user's own and carried in both of the hash service's digest sets, so the digest masks, the transcriber's match and the redactor catch them on any surface exactly as they catch the user's; the relationship word, daughter or nominee, is a non-sensitive task field the catalogue entry may name, and no person's name is ever a fact in clear. The brief fixes a Graphiti-style temporal graph; the library choice is recorded in DR-016. Sensitive fields live in the vault: the store holds the alias, never the value, and a fact about a PAN is a fact about {{pan}}. A health or legal matter is a class of its own in Table 3.1 in 03, {{health.condition}}, {{health.medication}}, {{health.result}} and {{legal.matter}}: it enters through the device form's health fields or a rail, is vaulted at the proxy, and is never in clear in the store, on a card, in a step's facts_in_clear or on a call caption; what a booking needs is the speciality or department, a non-sensitive task field the catalogue entry names, never the diagnosis.

9.1The fact schema

{
  "fact_id": "f_0281",
  "subject": "u_3f9a...",
  "predicate": "has-account-at",
  "object": "HDFC Bank",
  "value_alias": "{{account.hdfc}}",
  "sensitive": true,
  "source": { "kind": "task-outcome", "ref": "t_09/s_05" },
  "observed_at": "2026-08-20",
  "confidence": "high",
  "user_confirmed": true,
  "confirmed_at": "2026-08-21",
  "valid_from": "2026-08-20",
  "valid_to": null,
  "superseded_by": null,
  "quality_flag": null
}

This record is the canonical fact schema; Table 1.2 in 01 is the user's view of the same fields, and its five source values map onto the five kinds here: interview is onboarding, connector is connector, task step is task-outcome, user statement is user-statement, and passport-adapter is the fifth, for a fact a rail returned; its "sensitivity" is the sensitive flag, true when the value lives in the vault and value_alias carries the alias while object names only the class or the institution. Confidence is a four-point scale, confirmed, high, medium, low, set by the source kind and decayed by age: a user statement or a passport-adapter result starts high and reaches confirmed when the user confirms it; a fact inferred from an outcome starts medium; a connector's fact carries the connector's confidence; every fact drops one point after a period per predicate that the catalogue's fact thresholds imply (illustrative: an address after a year, a phone number after six months), and rises one point when a later task uses it without contradiction. User-confirmed is a separate flag, because a fact can be high-confidence and unconfirmed: a fact used in an irreversible step must be confirmed or come from a passport adapter; a fact used to fill a form the user will see before submission may be merely high; each step type's entry names the threshold it needs, and a fact below it becomes a question (section 9.4) rather than a guess.

9.2The temporal graph

Every fact has a validity interval, and a query is always made at a point in time: the planner asks what is true now, the audit asks what we believed when a step ran. A new fact that contradicts an existing one does not overwrite it; it opens with its own interval, the old fact's valid_to is set when the contradiction is resolved, and until then both carry a quality_flag. A flagged fact cannot be used by a step, and the flag propagates: the task service finds every open plan whose facts_used names the fact, re-plans it before the affected steps run, and turns the conflict into a question to the user at the next natural point, or into a blocked-needs-user step if a running task depends on it. A fact past its valid_to is never used. Facts are learned mostly by doing tasks: every ok outcome carries the facts the step established, written with the step as their source; the onboarding interview and read-only connectors top the store up, per onboarding in 01.

9.3Who reads and writes it

The planner reads the store through one query: subject, an optional predicate filter, a point in time, and a minimum confidence, answered with the facts valid at that time and their provenance; there is no free-text search and no query across users. The write path is one too: the task service takes the facts an ok outcome, an onboarding answer, a question's answer of any kind, a choice, a date or a free line, a connector pull or a rail response established, submits each to the hash service's screening call (section 8.3), which runs the same four detectors the vault's edge proxy runs, identifier pattern, with the date and amount patterns beside the identifier patterns, known-value digest, the user's declaration where the field is declared sensitive and the dictionary-based health and legal term detector, tokenises every match through its tokenise-only credential and returns the text with aliases in place, and appends only what the call returned, with the fact's source, so a sensitive fact, a condition a worker typed or a user answered included, is written as an alias; the store itself rejects any value that matches a pattern. The user reads their own store as a profile in which every fact shows its source and date and can be confirmed, corrected or deleted from their device; a correction is a new fact with the user as its source, and it re-plans any open task that relied on the old one. The audit function reads it too, by the point-in-time query of section 9.2, what we believed when a step ran, answered in aliases like every query and opened as a ledger event with the viewer's role; nothing else reads it, and its non-sensitive contents sit in the region the residency map assigns.

9.4Questions to the user

A question is a task-level record, not a step: question_id, the task, the step it blocks if any, the text in plain words, the predicate it would establish, the answer kind (a choice, a date, a free line) and an expiry. A question never asks for a value of an alias class: a missing personal fact, a date of birth, a name, a number, is asked for as a field of the device form of section 4.7, which posts to the vault's edge proxy and arrives as an alias. The three answer kinds are for non-sensitive task facts, and every answer of every kind is submitted at entry to the hash service's screening call like a result field, so that what is stored carries aliases in place of any match (sections 8.3 and 9.3). The planner raises a question when a fact is missing, flagged or below the step's threshold; the task service records question-asked, moves the task to awaiting-user by ask, and shows it on the device surface, never in the chat thread. The answer is written as a fact with source kind user-statement, confidence confirmed and the question as its reference, the task service records question-answered and resume, and the steps that depended on the gap are re-classified.
