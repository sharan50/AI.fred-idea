10The intake gateway

Every channel arrives at one door and leaves it as one format, already tokenised. The gateway accepts WhatsApp, the native app, SMS and iMessage, and the web, in text, voice and attachments, and produces the internal request record every other component understands; inbound mail, a reply on the task's thread fetched by the mailbox connector or forwarded by the user to the task's relay address, enters by the same door as a reply and is never a front door. Which channel is the front door in a market is a launch choice, held amber with its trigger in intake in 01 and recorded in DR-001; the gateway is the fixed decision underneath, and nothing downstream knows which channel a request came from.

10.1Tokenisation at the edge

The gateway is behind the first of the three doors a real value enters by, and it never holds a raw byte. The channel webhook, the device form and, in front of the adapters, every rail response terminate at the vault's edge proxy: a tokenising proxy the provider runs in the market's region under our detector policy, so the message body, every attachment and the audio of a voice note are the proxy's bytes and never the gateway's. Whether the chosen vault can run this proxy in region with our detectors loaded is a requirement of the vendor evaluation in 07; the proxy is a provider product configured with our detector policy, not a component we build, and the policy is four detectors we ship to it per market, the same four the hash service's screen runs over text written on our side (section 8.3): identifier-pattern detection for the value types each market knows (a PAN's form, an Aadhaar number's form, a card number's check digit, a National Insurance number's form) and for the amount pattern, a number with a currency word or symbol in written or spoken form, lakh and crore, thousand, rupees, pounds and dollars included, tokenised under the financial-fact class of Table 3.1 in 03 so that a balance, a transaction, a loan, a salary, an overdue sum or a quoted fee in a rail response, an inbound mail or a free text written on our side becomes an alias such as {{balance.hdfc}} or {{amount.fee}}, known-value matching against the digest set the hash service issues to the proxy, user declaration, where the user marks a value as sensitive or answers the device form, and a dictionary-based detector of health and legal terms that tokenises a free-text mention of a condition, a medication, a result or a legal matter in a message or a transcript under the health and legal class of Table 3.1 in 03, whose effectiveness is the to-verify item 03 carries. Each detected value is tokenised inside the proxy, and the alias takes its place; the proxy adds an aliases_issued header to the tokenised message, from which the gateway fills the field of the same name. Attachments are tokenised whole: the document image goes into the vault, and the request carries a document alias, the document type and the metadata the planner needs. A voice note is transcribed inside the proxy's boundary and the transcript tokenised the same way; the audio enters the vault as a document alias, and the request carries the alias transcript and the time span of every detected value, which is all the evidence pipeline ever receives of it. The gateway parses a tokenised message, holds no vault SDK and has no network route to the vault; if the proxy is unavailable the channel receives a retry response and no message is accepted, because fail closed here means no byte of a message reaches a process of ours. The outbound direction is the mirror: an acknowledgement, a nudge notification or a reply the gateway sends on the conversation channel is addressed to an alias, {{phone}} or a WhatsApp or iMessage handle, and the proxy's channel connector, an address-only role beside the substitutor's, resolves that address alias only to hand the message to the channel provider and returns nothing to any process of ours. A value is detokenised into a surface by the substitutor alone (section 4); the connector never resolves an alias into a message body, so a notification carries no value and no process of ours ever holds the number it went to.

Typing at detection is the proxy's, by the detector policy: a pattern detector types a value by its format and check digit, a known-value match types it by the alias it matched, and a declared value takes the type the user gave. A format two classes share, a sixteen-digit number that may be a card or an account, an unspaced ten-digit number that may be a phone number or an NHS number, is tokenised under the broader class, and the request carries the alias marked ambiguous, which the gateway resolves by asking the user to confirm the type in the device form before any step uses it. A value the detectors miss is this component's residual risk; the model runtime's separately deployed detector refuses to plan on a candidate value and returns the message for re-tokenisation, the default paints are the second line, the browser masker's on every frame (section 4.1), the mail relay renderer's on every inbound message a worker reads (section 4.3) and the card renderer's on every free-text field of a task card (section 3.2), with the same allowlist run by the evidence pipeline over its batch transcript of a call (section 8) and the known-value matching on every surface and in the evidence pipeline beneath them, and the threat model in 03 names the path.

Two rules from DR-001 are stated here as the gateway applies them behind the proxy. The pass fails closed: a message carrying a suspected value the detectors cannot type never becomes a task. The proxy holds the message in its own memory, in region, for the hold window of Table 2.8, the gateway asks in the channel for the value in a typed field, which is the device form, and nothing opens in received until the pass is clean; if no re-entry arrives before the window expires, the proxy discards the message unseen and the gateway tells the user that nothing was started. And the sender is bound before anything else: the proxy tokenises before the sender is known, so a message from an unknown number or address reaches the gateway tokenised, the gateway finds no user binding, replies with the onboarding route of onboarding in 01 and nothing else, discards the message, and instructs the proxy to destroy the aliases it issued; the message is never stored and never queued for a person.

Three rules follow from the format. The bounce channel is the device binding, never the channel the request came from: a one-tap approval on a chat thread would be an approval anyone holding the phone number could give, so bounces and envelope prompts go to the device surface, and the chat thread receives only a notification that something is waiting. A message that references an existing task routes to it: the gateway resolves thread_ref first by explicit reply and by a task reference in the text, and otherwise by one planner call over the tokenised message that returns a task id or none; the gateway runs before the planner plans, but it may ask it. A message that references two tasks, or one the planner call marks ambiguous, opens nothing and produces a question on the device surface naming the candidates, and the answer sets thread_ref. A message that references a task in a waiting state is attached to the task's timeline and, where the task is on the nudge schedule, resets that schedule to its start as a recorded nudge-reset (section 5.3); it is never a resume, because resume is only the awaited action itself, given on the device. A lapsed task gets revive; an active one gets the message attached to its timeline for the planner's next run. The locale rule is the third: scripts and result forms are rendered in the floor's working language, with the institution-facing sentences in the market's language where the party's directory entry says so; the field's kind and the party's mask map come from the catalogue; and ledger lines, nudges and the outcome report are rendered from fields in the user's locale. Refusals are not the gateway's job; a request outside what we do is refused in received or planning against what we refuse to do in 01 and the market's refusal list, and the user is told why.
