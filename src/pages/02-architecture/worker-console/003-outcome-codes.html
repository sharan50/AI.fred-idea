3Structured outcome codes

Exactly one code from the fixed vocabulary below closes a step, together with the structured fields that code requires, and the console will not submit a result until those fields are present. The vocabulary is the control loop specified in verification in 02: it decides what the task service does next, it is not a judgement of quality, and the user's verdict remains the only measure of that.

Table 2.4 The nine outcome codes, what each means and the fields the result form demands before it will close the step.
CodeMeaningRequired fields
okThe expected outcome was achieved.reference (if any), timestamp, party
ok-with-varianceAchieved, with a noted difference from the expected outcome (a fee, a date, a condition).as ok, plus variance note
blocked-third-partyA third party prevented completion for now (office closed, system down, callback promised).party, response window
blocked-needs-userA user-only act or fact is needed. Creates a user step.what is needed, why
blocked-outside-envelopeContinuing would exceed the envelope. Creates an extension request or a user step.the envelope line it would breach
failed-retryableA transient failure before any committing action; the step can be re-attempted by the same route. Not available once the step's fired marker exists.error class
failed-finalThe step cannot be completed by this route, or its committing action fired without confirmation. Triggers re-planning.reason, alternatives considered; the fired marker, attached by the task service where one exists
refused-policyThe executor declined under policy (for example, asked to reveal a real value, or the policy layer prohibits the step type in this jurisdiction).policy reference
supersededThe plan changed and the step is no longer needed.superseding step

The form is shaped by the code. Choosing ok reveals the reference, timestamp and party fields, with the timestamp set by the console and the party pre-filled from the envelope; choosing blocked-third-party asks for the response window as a choice from the step type's allowed windows rather than a free number; choosing blocked-outside-envelope asks which envelope line, from the lines on the card, and the task service turns it into an extension request whose device prompt offers "do this yourself" where the catalogue names a user-act form, which is the only way that code produces a user step; choosing failed-final asks what alternatives were tried, as a checklist from the step type plus a free line. A step whose controller or substitutor has written a fired marker, a submit issued, a relay release issued, a committing key sent, a committing sentence begun, a committing placement begun, cannot close failed-retryable: the form offers failed-final only, the task service attaches the marker as the evidence, and the re-plan issues a status enquiry before any repeat, so an unconfirmed act is never fired twice, as closing a step in 02 fixes. A worker cannot type a value into any field. The reference field, where a third party's booking or case reference goes, is filled by the surface controller with the alias the proxy issued for a message or the browser masker painted on a page. On a call there is no controller to fill it: the worker hears the desk read the reference out, because a call is not masked (DR-021), and types it into the result field, where the hash service's screen tokenises it before it is stored. Every free-text field on the form, the variance note, the failed-final free line, the demand a worker records, is submitted at entry by the console to the hash service's screening call in 02, which runs the same four detectors the vault's edge proxy runs, identifier pattern, known-value digest, the user's declaration and the dictionary-based health and legal term detector, tokenises any match through its tokenise-only credential, a reference-shaped span under the reference class, a condition under the health and legal class, each with a "received" ledger line, and returns the text with aliases in place; the console stores only what the call returns, and the outcome record carries those aliases thereafter. Scripts still instruct the worker to ask a party that issues a new identifier, an account, policy or application number, to send it by the mail relay or to the user directly rather than read it aloud, but that instruction closes nothing: the worker hears the desk read the reference out, because a call is not masked (DR-021), and types it into the result field, where the hash service's screen tokenises it before it is stored, the caption reading "reference captured as {{reference.max-healthcare}}", as telephony in 02 fixes; a worker who needs a masked span to proceed asks the party to send it on the task's thread, where it is tokenised on arrival, or closes the step blocked-needs-user; the pipeline's second pass, which flags a span the transcriber should not have delivered and opens an incident, is the record, never the closure, and the threat model in 03 carries the path with the allowlist as its closure. superseded and refused-policy after a refused placement are never chosen by a worker; the task service applies them. Artefacts attach automatically from the evidence pipeline; a worker neither selects nor sees them.
