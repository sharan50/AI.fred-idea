1The harness-first build sequence

We build the harness in the order the two fatal failures dictate, and before anything a customer can see. The alias vault and the substitutor come first, so that no later component ever handles a real value. The authority envelope and the classifier come second, so that no later executor can fire a step outside its grant. The state machine and the watchdog come third, so that no task can be forgotten once tasks exist. Only then do we build a surface on which a step can run. Figure 6.1 draws the eight stages in order, with what each one makes possible.

The sequence is ordered by preconditions, not by calendar. Each stage has a gate: a test that must pass before the next stage starts, stated below in terms an engineer can automate. No dates appear on this page, because the only honest date is the one a gate produces; a stage that has not passed its gate is not late, it is unfinished.

The order a demo prefers, intake channel and browser agent first with the vault bolted on later, is rejected: every surface built before the alias rule has handled real values, every log written before it contains them, and the threat model in 03 would have to close paths that need never have existed.

Stage 1: alias vault and substitution
The vault is bought (DR-008) and the substitutor is written: the one small service with detokenise rights, in its own environment, taking task id, step id, alias, surface and target descriptor, injecting directly into a surface and never returning a value. The alias grammar ({{pan}}, {{account.hdfc}}) and the two tokenising edges, intake and adapter boundary, are built as libraries now. Gate: the vault SDK is absent from every build artefact except the substitutor and the two edges, checked by the build; no other component can detokenise; the substitutor writes a ledger entry on every call.
Stage 2: envelope and classifier
The envelope schema with its five fields, the point-of-no-return test, the rule of classification, and the policy layer as a loaded flag table (the first market's, in draft); the planner learns to propose an envelope with every plan. Gate: a step library for the pilot's task types in which every step carries a class and a reversibility; a classifier evaluation set; an executor-side check, in the substitutor and in every executor, that refuses any step outside the envelope. The envelope a user sees in 01 is the object the harness enforces.
Stage 3: state machine and watchdog
The states, transitions, timers and nudges of the state machine in 02, lapsed as a state only the system assigns, and the watchdog that feeds the exceptions board. Gate: the invariant survives fault injection (delete a timer; the task must reach the board before anything else happens); every transition is recorded with its cause; no code path reaches a terminal state without a named transition. Tasks can now exist: a user can go quiet safely, and we cannot forget.
Stage 4: the managed browser
The first execution surface, and the accent in the figure: our browser, the substitutor's driver typing the value into the field, the worker's stream rendering it as dots, DOM capture masked by known-value matching. The evidence pipeline (capture, redact, verify, store) ships inside this stage, not after it, because this is the first moment a real value exists outside the vault. Gate: a canary test plants a known value and proves it appears in no stored artefact, no log and no frame a worker can see; the verify pass fails closed. ai and human steps can now run on any web form, which is most of the wedge.
Stage 5: telephony and mail relay
Our numbers on a bought carrier platform, one call leg per party, the value spoken as synthesised speech or sent as keypad tones on the far leg while the worker's leg is muted and their panel shows "value placed"; transcripts alias-replaced before storage; the relay swapping aliases into outbound mail after composition. Gate: the canary test repeated on audio, transcript and mail; a recording that fails the verify pass is destroyed, never stored; the relay holds no raw value at rest.
Stage 6: worker console
The task card, alias-only rendering, the outcome-code vocabulary, the dual-control check and the exceptions board, as the worker console page specifies them. Gate: the console cannot render a real value, because the vault SDK is not in it and the alias grammar is all it can show; the invariant appears in it identically to 02; the L1 pool has run a shift on it against synthetic tasks.
Stage 7: the access ledger
The entries have existed since stage 1; this stage renders them per task, in plain words, on the user's device, as the ledger specification in 03 sets out. Gate: every line maps to exactly one substitutor call; the ledger holds aliases and never values, tested against the threat model's evidence paths; a user can read a task's ledger without asking us. The trust story becomes something a customer checks.
Stage 8: intake gateway and first adapters
The channel-agnostic gateway normalising every channel into one request format and tokenising any typed or uploaded value at the edge; the universal device bounce-back; the first market's passport adapters, tokenising at their boundary. The front door is the per-market choice of DR-001. Gate: a planted value typed by a user is an alias before the planner sees it; an adapter cannot return a raw value; the bounce-back works with no adapter at all. A real user can now arrive, and therefore the pilot can open.

2Pilot scope in capability terms

The pilot is scoped by what the harness can do safely, not by how many people use it or what they pay. Five things define it: the verticals in scope, the step classes and reversibility the harness executes, the identity acts it delegates, the surfaces it runs on, and the market it opens in. The first four are fixed here; the fifth is open.

2.1Verticals

Three of the six marquee verticals open the pilot: banking and wealth, identity and security, and legal and administrative. Every task in them exercises the substitutor and the envelope, so the pilot tests the promise itself and not a proxy for it. Health and medical joins when stage 5 has passed its gate and an L2 health pod exists, because health tasks live on booking lines. Travel and family affairs join last: they carry less consequence and are where the flat-fee category lives (see the landscape in 00); they are on the roadmap because a household delegates all of its admin to one assistant, not because they prove anything about trust.

2.2Step classes and reversibility

In the pilot, ai steps run only on the managed browser; human steps run from task cards on every surface that has passed its gate; user steps bounce to the user's device without exception. Reversible steps inside the envelope execute. Irreversible steps inside the envelope execute under dual control, with the L3 super-trust tier as the checking party for the whole pilot, whichever party executes. Irreversible steps outside the envelope bounce; reversible steps outside it become extension requests. Envelope defaults per task type are set narrow and widened by the user deliberately.

2.3Delegated identity acts

Only the identity act types the first market's policy layer flags as delegated are delegated; everything flagged bounce, or prohibited pending a regulatory answer, stays with the user even where the user ticks it. The pilot's flag table is the first draft of that market's lobbying agenda (the policy flags in 03), and every prohibited line is a legal to-verify with an owner in 07.

2.4Surfaces

The managed browser from the first task; telephony and the mail relay once stage 5 has passed its gate. A worker never uses a tool of their own, in the pilot as afterwards, and the refusals in 01 apply unchanged.

2.5Which market first

Which market the first cohort lives in is an open decision, listed in 07 with an owner and a trigger; this page does not pre-empt it. What the decision changes is bounded: the adapter set, the legal pack, the shift on the wheel and the front-door channel of DR-001. It changes none of the eight stages; the harness is built in Bengaluru whichever way it goes, as the markets section of 00 sets out. One build, three possible first doors.

What the pilot must produce is fixed too: verdict rates per task type joined to step traces, the improvement loop of DR-002; the exceptions-board history; a ledger for every task; and the measurements 05 names for the day economics reopens. The pilot opens when every gate has passed and a person who did not build the harness has hunted the two fatals through it and found nothing.

3Build versus buy

We buy what must be boring and audited and build what carries the promise. Four components are bought: the tokenisation vault, telephony, the browser sandbox and the models. Seven are built: the planner, task cards, the substitution component, the authority envelope, the state machine, the worker console and the access ledger. Table 6.1 gives the reason for each and what the choice commits us to; buying is a commitment to someone else's roadmap, regions and outages, and the table says so.

Nothing built sees a bought component's raw output without a tokenising edge in between, and the vault, the sandbox and the carrier are named paths in the threat model, not trusted boxes.

4The country-expansion playbook

A new country is an adapter, a legal pack and a shift, and nothing else changes. That is the decision of DR-007: the universal core is one build, country-agnostic, and entering a country must not touch it. The checklist below is what we run for each of the three markets and for any fourth. A country is live when every line is ticked, and not before.

4.1The adapter

  1. Inventory the country's rails: identity, documents, bank data, payments, signatures, and the institutions the wedge verticals touch.
  2. For each rail, choose one of three routes: integrate directly where the rail admits us; integrate through a regulated partner where the rail is reserved to regulated entities; bounce to the user's device where neither is open.
  3. Build the passport adapter behind the adapter boundary, as the adapter model in 02 draws it: it tokenises every value it receives before the planner sees it and returns aliases only.
  4. Pass adapter conformance: a planted value cannot cross the boundary; every consent artefact and its expiry is a dated fact in the context store.

4.2The legal pack

  1. Load the policy flag table: per step type, delegated, bounce, or prohibited pending a regulatory answer. Every prohibited line becomes a lobbying-agenda entry with its end-user benefit stated.
  2. File the KYC last-mile constraints as legal to-verifies with owners in 07. Design carries the ceiling; the flags carry the law.
  3. Add the country to the data-residency map: vault region, evidence-store region, inference region, and the safeguards for staff in Bengaluru processing the country's data, which for the UK is a restricted cross-border transfer needing contractual safeguards to-verify.
  4. Extend the privacy-law skeleton in 03 and record the consumer-law liability position, since it is our name on the agent.
  5. Settle the contactable-party defaults and the refusals list for the country.

4.3The shift

  1. Place the country on the 24/7 wheel in 04: the shift that covers its business hours and the handovers either side.
  2. Stand up the L2 pods for the verticals opening in that country, with QA and escalation cover on the same shift.
  3. Provision the country's numbers, caller identity and languages on our telephony, and the substitution stations under the site controls, which do not vary by country.
  4. Render the ledger in the country's plain words and check that the trust story reads true there.

The three markets are instances of the same list, with preconditions the research to date can state only partly.
