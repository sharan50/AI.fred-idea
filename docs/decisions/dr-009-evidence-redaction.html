DR-009Evidence redaction as part of the harness

Every screenshot, recording, transcript and DOM capture is redacted inside the harness before it is stored, checked by a second independent pass that fails closed, and no raw artefact is ever human-viewable. The evidence system is a path by which a human could see a real value, and the threat model treats it as one.

On this page

1Decision

Evidence is redacted inside the harness before it is stored, and no raw artefact is ever human-viewable. Every screenshot, recording, transcript and DOM capture, and the call metadata beside them, passes through one pipeline in a fixed order: capture, redact, verify, store. Redaction applies five artefact masks in the fixed order 03 specifies: coordinate masks at the points where the substitutor placed a value, with a margin, from the frame of placement to the frame of navigation; known-value masks by keyed digest, the digests issued by the hash service and never the values, over text layers, document captures and transcripts; audio windows, the transcriber's allowlist run inside the pipeline over the raw audio as it runs live, so that every placement, every matched read-back and every span the allowlist withheld is replaced with silence, the transcript naming the alias for a placement or a match and reading "span masked" where the live caption did; format masks, every run or span that matches a class format of Table 3.1, the party's recorded reference shapes or the health and legal dictionary; and mask-map masks, every run and figure the step's mask map does not clear. Aliases replace matches in transcripts and document captures, so a transcript reads {{dob}} where the value was, and a stored recording or transcript holds no span the live leg withheld from the worker. Verification is a second, independent pass by a separately built service with its own digest set under a second key; it checks the allowlist's windows as it checks known values, formats and the mask map, and it fails closed. An artefact that fails is never written: it is quarantined in memory, an incident opens naming only the alias and the rule that missed, redaction re-runs from memory with wider masks, and after a small fixed number of attempts the raw material is dropped and the step's evidence becomes a structured note, "evidence withheld: redaction could not be verified". Nobody views the quarantined artefact, the incident handler included; the handler receives the redaction manifest and the id of the matched digest and nothing else. The step keeps its outcome code, and the user's ledger records that the artefact was destroyed rather than kept. Raw artefacts exist only in the pipeline's memory. The pipeline ships inside the managed-browser stage of the build sequence, because that is the first moment a real value exists outside the vault.

1.1The evidence system is a leak path

Artefacts are where the world echoes values back. A confirmation page shows the account number the substitutor just typed; a booking line reads a date of birth back to check it; the form we filled sits whole in the screenshot. Left raw, the evidence store would hold more real values than any other component, and it is the store people most want to open: for dispute, for audit, for QA, for training. So the threat model in 03 names the evidence system as a path and closes each of its parts: pipeline memory, the store, the viewer, exports and any recording a provider keeps. The wider field shows why a stored copy matters whatever the front door does: TechCrunch reported in August 2026 that Instinct, an AI assistant, stored email in plain text and went on producing inbox summaries hours after access to the mailbox had been revoked verified [1].

1.2What redacted evidence is for

Audit and dispute only, as DR-002 fixes, and the whole access list is Table 3.3 in 03: the QA and escalation function opens a masked artefact for a dispute, a wrong-outcome or could-not-complete verdict, a refused-policy exception or the shift lead's sampling of closed steps under the QA duty in 04; the user opens their own, on request from their device; a legal request goes through the legal pack's procedure; engineering sees manifests and counts and never an artefact. An artefact is never pushed to the user as proof of completion and never used to train a model. A worker sees the live masked stream during a step, with the placed value rendered as dots and any echo of a known value masked by hash matching before the frame is encoded, and never a recording afterwards. Every opening of a redacted artefact is itself a ledger event naming the viewer's role and the reason, so the evidence store carries its own ledger.

1.3Where it is specified

The five artefact masks and the fail-closed rule are specified in 03; the pipeline is drawn as Figure 2.4 in 02; the gate is stated in 06: a canary test plants a known value and proves it appears in no stored artefact, no log and no frame a worker can see.

2Rejected alternative(s) and their cost

Redaction as an operational policy
Store artefacts raw, restrict who may open them, and tell workers not to look. A raw store then exists, so a path exists; a policy is a procedure rather than an invariant, and the threat model would show the path open. A breach of that one store would be a breach of every task ever run.
Redact at display time
Mask in the viewer and keep the original underneath. Backups, exports, support tooling, crash dumps and the provider's own copies never pass through the viewer, and each is a fresh path.
Keep no evidence at all
Dual control would have nothing to check against, a dispute would be one account against another, and the access ledger's line "no person saw it" could never be audited. The cost of no evidence is a promise nobody can test.
One redaction pass, no independent verification
A pass that misses a single value stores it forever. The second pass is built and run separately from the first and shares no code with it, so the two do not share a defect, and its failure opens an incident without ever putting the artefact in front of a person.
Artefacts as customer-facing proof
Rejected in DR-002 and restated here: an artefact pushed into the outcome report as proof invites a viewing habit, on our side or the user's, that turns a sealed store into an open one. The user's own masked artefacts stay available on request, as a logged act; the report carries the ledger instead.

3What this closes off

  • A raw artefact persisted anywhere: store, crash dump, debug log, pipeline error path, or a provider recording we have not redacted.
  • A viewer with a show-original control, or any role that can see an artefact before the verify pass has passed it.
  • An artefact stored after the verify pass fails, or stored while verification is pending.
  • An export path that leaves the pipeline, including support tooling and analytics.
  • Artefacts used as training data, pushed to the user as proof of completion, or opened by anyone the access list in 03 does not name, for an occasion it does not name.
  • A quarantined artefact viewable by an incident handler, or kept in memory past the fixed number of re-redaction attempts.
  • An execution surface that ships before its redaction ships with it.
