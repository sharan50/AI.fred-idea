On this page

1Decision

We build one intake gateway. It accepts WhatsApp, a native app, SMS and iMessage, and the web, and normalises each into one internal request format carrying text, voice and attachments; every component behind it, the planner first, sees that format and nothing else. The front door, the channel a market launches with, is a per-market choice, not an architecture commitment; today it is amber.

1.1What the gateway does

Three jobs, in order. It binds the sender to a user account: a message from an unknown number or address is never a task; it gets the onboarding route in 01 and nothing else, and it is never queued for a person. It normalises what the vault's edge proxy hands it: the alias transcript of a voice note, transcribed inside the proxy's boundary; the document alias, type and extracted fields of an attachment; a thread as one request; the channel as a field. And it issues the request record 02 specifies, with every alias the proxy created listed for the ledger. Tokenisation is not the gateway's act. The channel webhook and the device form terminate at the vault's own tokenising proxy, run by the provider in the market's region under our detector policy, so the message body, every attachment and the audio of a voice note are the proxy's bytes and never the gateway's; the gateway receives {{pan}} and a document alias, never the digits or the image, holds no vault SDK and has no network route to the vault. That proxy is the first of the three doors a real value enters by; the alias model in 03 names all three.

The four detectors 02 specifies run at the proxy, identifier pattern, known-value digest, the user's own declaration and the dictionary-based health and legal term detector, and the pass fails closed. A message carrying a suspected value the detectors cannot type never becomes a task, as 02 fixes: the proxy holds the message in its own memory, in region, for the hold window of Table 2.8, the gateway asks in the channel for the value to be entered in a typed field on the device, which is the device form, and nothing opens in received until the pass is clean; if no re-entry arrives before the window expires, the proxy discards the message unseen and the gateway tells the user that nothing was started. Nothing is held on our side at any point, because no raw byte ever reached a process of ours. A value no detector suspects is the residual risk 02 names: the model runtime's own detector returns such a message for re-tokenisation before it plans, known-value matching on every surface is the line behind it, and the redaction section of 03 specifies the maskers.

The front-door choice never changes where authority is given. A confirmation, an envelope edit, a bounce approval and a verdict are taps on the authenticated device on the user record, the device_binding of 02's request format, never on the chat thread. For a chat-only front door the channel carries the prompt and a link, and the tap happens in our app or the logged-in web view, whichever the market launches with. A thread bound only to a phone number therefore never approves an irreversible act, and the door changes neither the plan nor the envelope.

1.2Why the front door is amber

The markets do not share a habit. India's leading players run on chat plus human assistants: Hulp takes requests through its app, WhatsApp, a call or a text verified [1], and M, from Dunzo's co-founder, works through WhatsApp verified [2]. WhatsApp is therefore the natural India candidate, and the founder's earlier notes chose it.

The west is not settled. In London Samwise runs on WhatsApp, phone and email verified [3]; in the US Pally lives in iMessage and the user's own mail and chat tools verified [4]. Until the first US/UK cohort is scoped we do not know which door those users will use, so we fix the gateway and hold the door open.

2Rejected alternative(s) and their cost

A WhatsApp-native product
The Indian field's default and the founder's earlier choice. Intake takes the shape of one vendor's message model and business-messaging rules, the planner inherits that shape, and the second market means re-plumbing intake and re-proving the proxy termination. It also decides the western front door by accident.
A native app only
Clean to build, and the wrong side of the habit the Indian field has proven: an install and a sign-up before first value. Worse, it fixes the front door for every market at once, the commitment the amber refuses.
Per-channel intake, built as each channel arrives
Each channel becomes its own parser, identity binding and proxy termination to prove leak-free; the threat model in 03 gains a named path per channel, and the request format drifts into several.

3What this closes off

  • Any component behind the gateway that branches on channel: it is a field on the request, never a branch in the planner, the classifier or the envelope.
  • A real value reaching the planner, the model, a worker or the context store from any channel, including ones added later.
  • A raw byte of any channel held by the gateway or by any process of ours: every channel terminates at the vault's edge proxy.
  • A second request format, whatever the door.
  • A front door chosen for architecture reasons rather than a market's habit, or one not reversible by configuration.
  • Adding a channel as a project that touches anything behind the gateway.
  • An approval accepted from a channel that authenticates only a phone number.

4Status

The gateway is a fixed decision, taken by the founder and recorded in the brief's ledger on 2026-09-02. The front door is amber: WhatsApp leads for India, and no candidate is fixed for the US or the UK. 01 states the amber and its trigger at intake, and the item has an owner in 07. A reply fetched from the user's own mailbox by its connector, or forwarded by the user to the task's relay address, enters by the proxy like any channel and is bound to its task by the thread, so the one request format and the proxy termination hold unchanged under DR-018.

5Trigger

Resolve when the first US/UK cohort is scoped, by naming the front door for each launch market and recording it here as a revision; the gateway is untouched. The earlier PRD's channel choice, WhatsApp, is reconciled by this amber: it stands as the India candidate and nothing more. No prior PRD exists in this repository; the rule was applied to an absent document, and any later-found copy is reconciled here.
