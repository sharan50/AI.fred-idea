On this page

1Decision

We build one intake gateway. It accepts WhatsApp, a native app, SMS and iMessage, and the web, and it normalises each into a single internal request format that carries text, voice and attachments. Every component behind the gateway, the planner first among them, sees that format and nothing else. The front door, meaning the channel we put in front of a market at launch, is a per-market choice and not an architecture commitment; today it is amber.

1.1What the gateway does

Three jobs, in order. It binds the sender to a user account: a message from an unknown number or address is never a task, is answered only with the onboarding route in 01, and is otherwise discarded, never stored and never queued for a person. It normalises: a voice note is transcribed, an attachment is typed and its fields extracted, a message thread becomes one request, and the channel it arrived on is recorded as a field rather than as a shape. Transcription and attachment description run inside the gateway's own isolated boundary, so the raw audio or image is never persisted and never human-viewable, and the original is held only as redacted evidence. And it tokenises at the edge: every real value is swapped for an alias before the request leaves the gateway, so the planner receives {{pan}} and a document alias, never the digits or the image. The gateway is one of only three points at which a real value may enter the system; the alias model in 03 names all three and the intake gateway in 02 specifies the format.

Detection is a rule set, not a guess. Typed fields and the user's own declaration capture the formats we know; format and entity detection runs on free text and on every transcript; known-value matching against the vault's hashes catches a value the user has given us before wherever it recurs, an attachment's extracted fields included. The pass fails closed. A request carrying a suspected value that the detectors cannot type with confidence is held in received, the user is asked to re-enter it in a typed field, and nothing leaves the gateway until the pass is clean. A value no detector suspects is the residual risk 02 names; known-value matching on every surface and in the evidence pipeline is the second line, and the redaction section of 03 specifies both the rule set and the masking it feeds.

The gateway carries the conversation in both directions, and the front-door choice never changes where authority is given. A confirmation, an envelope edit, a bounce approval and a verdict are always taps on a surface that authenticates the user: our app, the web with a login, or a channel whose device binding the passports section of 03 accepts. The channel may carry the notification and the link and nothing more, so a chat thread bound only to a phone number can never approve an irreversible act, and the choice of door changes neither what the planner produces nor what the envelope permits.

1.2Why the front door is amber

The markets do not share a habit. In India the leading players run on chat plus human assistants: Hulp takes requests through its app, WhatsApp, a call or a text verified [1], and M, the household assistant from Dunzo's co-founder, works through WhatsApp verified [2]. WhatsApp is therefore the natural India candidate, and the founder's earlier notes chose it.

The west is different and not yet settled. In London the new entrants are WhatsApp assistants: Samwise runs on WhatsApp, phone and email verified [3]. In the US the text-native entrant Pally lives in iMessage and the user's own mail and chat tools verified [4]. Until the first US/UK cohort is scoped we do not know which door those users will walk through, so we fix the thing that does not depend on the answer, the gateway, and hold the answer open.

2Rejected alternative(s) and their cost

A WhatsApp-native product
The Indian field's default and the choice in the founder's earlier notes. Its cost is that intake takes the shape of one vendor's message model and business-messaging rules; the planner inherits that shape; and the second market means re-plumbing intake and re-proving edge tokenisation on a new surface. It also decides the western front door by accident.
A native app only
Clean to build, and the wrong side of the habit the Indian field has proven: an install and a sign-up before first value. Worse, it makes the front-door choice for every market at once, which is exactly the commitment the amber refuses.
Per-channel intake, built as each channel arrives
Each channel becomes its own parser, its own identity binding and its own edge tokeniser to prove leak-free. The threat model in 03 would gain a named path per channel, and the request format would drift into several.

3What this closes off

  • Any component behind the gateway that depends on which channel a request came from. Channel is a field on the request, never a branch in the planner, the classifier or the envelope.
  • A real value reaching the planner, the model, a worker or the context store from any channel. Tokenisation at the edge is the gateway's job on every channel, including the ones added later.
  • A second request format. Text, voice and attachments arrive in one shape whatever the door.
  • A front door chosen for architecture reasons. The choice is made on a market's habit, per market, and is reversible by configuration.
  • Adding a channel as a project that touches anything behind the gateway.
  • An envelope confirmation or a bounce approval accepted from a channel that authenticates only a phone number.

4Status

The gateway is a fixed decision, taken by the founder and recorded in the brief's ledger on 2026-09-02. The front door is amber: WhatsApp is the leading candidate for India, and no candidate is fixed for the US or the UK. The product page states the amber and its trigger at intake in 01, and the item sits with an owner in 07 open items.

5Trigger

Resolve when the first US/UK cohort is scoped. Resolving means naming the front door for each launch market and recording it here as a revision; the gateway is untouched by the answer. The earlier PRD's channel choice, WhatsApp, is reconciled by this amber: it stands as the India candidate and as nothing more. No prior PRD exists in this repository, so the brief's reconciliation rule was applied to an absent document, and this record is where any later-found copy is reconciled against the ledger.
