DR-011A visual token-and-component system

Every colour, type role and spacing value is a token in one file; every component is defined once in one stylesheet and composed on every page; no page carries styling of its own. A framework and per-page styling were rejected. The plan built on this decision is DR-012, and the harness enforces the rule on every pass.

On this page

1Decision

The publication has one visual system, held in two files and composed everywhere. tokens.css is the only place a colour is defined: paper, ink, line, accent, amber and verified as the brief gives them, two derived neutrals, and the type scale and spacing steps. base.css defines the reset, the typography and every component once: masthead, page header with stamp and control block, rail, status chip, reference and sources list, decision record, figure block, data table, callout, ledger, invariant and footer. print.css carries the print rules. The diagram language is a set of classes in the same stylesheet, so an SVG carries no colour or font attribute of its own. A page is markup plus class names and nothing more. A new layout on a future page means extending tokens and components first, then using them.

1.1Why tokens

One place to refine a value when contrast demands it, and one place for the harness to look. Because every colour is a named token, tools/verify.mjs can compute AA contrast for each text pair and fail the build when a pair falls short, and it can scan every other file for a hex, rgb or hsl literal and reject it. A page cannot invent a colour, so the accent cannot creep from the stamp into a link, and the brief's rule that the accent is spent on stamps and one stroke per figure is a property of the system rather than a request to writers.

1.2Why components once

The founder's bar asks for two things a component set delivers and nothing else does: every page reads as one designed publication, and any single URL stands alone in front of an investor. Both are made by sameness. The same masthead names the venture on every page; the same stamp and control block say how settled the page is; the same chip means the same thing in a thesis and in a threat model; the same figure block and table rule appear wherever there is a figure or a table. Sameness is guaranteed only when there is one definition, and one definition is what let this edition be written by several writers in parallel who never saw one another's pages: each copied one template and used the class names, and the design was never in their hands.

1.3How the rule is enforced

The harness rejects a colour literal outside the token file, a named colour anywhere, an inline style attribute, a per-page style block, and each of the brief's anti-defaults: uppercase transforms, tracked-out letter-spacing, gradients, box shadows and animation. It checks that every page links the two stylesheets and the print stylesheet, that every SVG uses classes rather than attributes for colour and type, and that each figure carries exactly one accent element. Style drift is therefore a build failure, found on the pass after it happens.

2Rejected alternative(s) and their cost

A CSS framework, utility library or UI kit
Every kit ships the defaults the brief bans: rounded cards with soft shadows, gradient washes, all-caps eyebrow labels, and a look shared with every generated documentation site. It arrives as an asset that dwarfs the content and usually wants a build step to trim, which DR-010 forbids. The cost of rejecting it is writing a few hundred lines of our own CSS once.
Per-page styling
Each page with its own style block or inline styles. Drift begins with the second page and a fix has to be made as many times as there are pages; the harness cannot compute contrast on values it cannot find; and a single URL stops reading as part of the publication. Within a few pages the visual system becomes archaeology.
Colours defined where they are used, without a token file
Custom properties scattered through the stylesheet meet the letter of "one stylesheet" and defeat the scan. The brief names one place for colours, and the harness needs one place to read.
A design-tool export
Generated CSS with literal values, opaque to a reader and rejected by the harness on its first pass. The design plan in DR-012 was written as prose and a wireframe so that a person can critique it.

3What this closes off

  • A hex, rgb or hsl value outside tokens.css; a named colour anywhere.
  • Inline style attributes, per-page style blocks and per-page stylesheets.
  • A component used on a page that is not defined in base.css, and a page kind outside the four the design plan fixes.
  • Uppercase transforms, positive letter-spacing, gradients, box shadows and animation.
  • A second type family, a synthesised weight, or a font loaded from anywhere but our own assets directory.
  • A colour or font attribute inside an SVG.

4Status

Fixed decision, set by the brief's visual system and taken at the start of the build on 2026-09-02, before any CSS was written. The plan built on it, critiqued against the generic defaults and fixed, is DR-012; the harness enforces both on every pass.
