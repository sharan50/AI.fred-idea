1Overview

The harness is a control system wrapped around a planner, not a chat model with tools attached. A request enters through one gateway, becomes a plan of classified steps, and each step executes on a surface we own, closes with a code from a fixed vocabulary and leaves behind a redacted artefact. Real values exist inside our boundary in exactly one component, and only for the moment of placement. Every task sits in one named state with a live timer until a recorded transition ends it. Those three sentences are the architecture; the rest of this page is their consequences.

This page is written for the engineer who builds the harness. It uses the vocabulary of the publication without redefining it: a task is one user request from intake to a terminal state; a step is the unit of execution and classification; a worker is a person on our side who executes a step from a task card; the user is the customer who delegated the task. The companion page, the worker console, specifies what a worker sees. The trust mechanics that this architecture exists to enforce are specified in the alias model in 03 and closed path by path in the threat model in 03.

Each component has one responsibility, and the boundaries between them are where the guarantees live.

Intake gateway
Normalises every channel into one internal request format and tokenises sensitive values at the edge, before any other component, model or person sees them. Specified in section 10.
Planner
Turns a request into an ordered plan of steps and an authority envelope proposal, and re-plans when outcomes require it. Section 2.
Classifier
Stamps every step with its class (ai, human, user), its reversibility under the point-of-no-return test and its route against the envelope. Section 3.
Policy layer
The per-jurisdiction flag table, consulted at runtime, that decides which step types are delegated, which bounce to the user's device and which are prohibited pending a regulatory answer. The mechanism is core; the table is per country and lives in the policy flag table in 03.
Envelope
The per-task grant of authority: spend cap, contactable parties, committable acts, delegated identity acts, validity window. Every execution decision is checked against it. The user's view is in the envelope in 01; the record format is in section 7.
Task service and state machine
Owns every task's state, every step's state, every timer and every transition, as an append-only event log. Section 5.
Execution surfaces
The managed browser, our telephony and our mail relay. The only places a real value exists outside the vault, and only for the moment of placement. Section 4.
Substitution component
The one small isolated service with detokenise rights. It swaps a real value into a surface at the last boundary and writes the ledger entry. It never returns a value to its caller. Its isolation is specified in the substitution component in 03.
Vault
The bought tokenisation service that holds real values and issues aliases. Regionally hosted per market. Outside our boundary by decision, recorded in DR-008.
Evidence pipeline
Captures, redacts, verifies and stores every screenshot, recording, transcript, DOM capture and call record. No raw artefact is ever persisted or viewable. Section 8.
Context store
The user's profile as a temporal knowledge graph in which every fact carries source, date, confidence and whether the user confirmed it. Section 9.
Worker console
The only screen a worker uses. It renders task cards and the surface panels, and it cannot render a real value because none reaches it. Specified on the worker console page.
Access ledger
The per-task, plain-words record of every use of every alias, readable by the user. Written by the substitution component and the surfaces. Format in the access ledger in 03.
Passport adapters
Per-country integrations to identity and financial rails, plus the universal device bounce-back. Each tokenises inside its own boundary before anything reaches the planner. Section 6.
The user's device
Outside our boundary. Where every user step lands as a one-tap approval or a user-performed act, where the envelope is confirmed and edited, and where the ledger and the verdict live.

Three boundaries carry the guarantees. Our trust boundary encloses every component that handles aliases; the vault SDK is absent from the model runtime, the worker console and the logging pipeline, so nothing inside can detokenise except the substitution component. The user's device is where authority originates and where irreversible acts outside the envelope are performed by the user, never by us. The vault sits outside because a tokenisation service is a bought commodity whose regional hosting is part of the residency answer, and because a boundary we do not operate is a boundary our staff cannot cross. The harness-first build order that follows from this map is in the build sequence in 06; the build-versus-buy line is in the build-versus-buy table in 06.

2The planner

The planner's output is a plan and an envelope proposal, and its contract is that neither contains a real value. It consumes the normalised request from the gateway, the facts the context store holds about the user that bear on the request (each with its confidence and validity), the task taxonomy's step templates from the taxonomy in 01, the policy layer's flag table for the user's market, and, when re-planning, the task's existing envelope and its closed steps. The model call is structured: the planner is a model with a schema-validated output, and the harness rejects any plan that fails validation before anything else happens. Because the model runtime has no vault SDK and the request reached it already tokenised, the planner cannot leak what it never held.

2.1Input and output

A plan is an ordered list of steps. Each step carries a purpose in one sentence, a proposed class, the surface it will run on, the party it will contact, the act type it will commit, the fields it needs as aliases, an expected outcome written as a testable statement, a deadline and a reversibility hint. The classifier then stamps the authoritative class, reversibility and route on every step; the planner proposes, the classifier decides. The envelope proposal is sized to the plan: the smallest spend cap, the shortest list of contactable parties, the fewest committable and identity acts, and the narrowest validity window that let the plan complete. A plan that needs more authority than the user's standing preferences allow is still proposed, with the excess marked, so the user sees exactly what they are being asked to grant. The planner also writes the plan summary in plain words that the user confirms; that summary and the envelope go to the user's device together, and no step executes before the user authorises them.

{
  "plan_id": "p_12.1",
  "task_id": "t_12",
  "summary": "Book the earliest cardiology appointment next week
              with Max Healthcare, then add it to your calendar.",
  "steps": ["s_01", "s_02", "s_03", "s_04"],
  "envelope_proposal": "env_12.1",
  "facts_used": [
    { "fact": "f_0281", "confidence": "high", "user_confirmed": true }
  ],
  "produced_at": "2026-09-02T14:31:40+05:30",
  "supersedes": null
}

Every plan records the facts it relied on and their confidence at the time. When a fact later changes, the task service can find every open plan that depended on it.

2.2Re-planning triggers

Re-planning is a recorded event, never a silent edit, and it never touches a step that has already fired. A step the new plan no longer needs closes with the code superseded; a step in flight is allowed to close first. The triggers are fixed:

  • A step closes failed-final: the route is exhausted and the planner must find another, or report that none exists.
  • A step's blocked-third-party response window expires: the task service raises escalate-resume and the planner proposes a new route around the silent party.
  • The user approves an envelope extension: classification re-runs for every affected step, because a step that was outside the envelope may now be inside it.
  • The user narrows the envelope: every step not yet fired is re-checked, and any step now outside the envelope becomes an extension request or a user step.
  • A blocked-needs-user step resolves with a new fact: the planner incorporates it and re-classifies the steps that depended on the gap.
  • The verdict is wrong-outcome: the parent task closes with that verdict and a linked child task opens in planning with the parent's trace attached.
  • A lapsed task is revived by a user message that references it: it re-enters planning so that stale steps are re-checked against the world as it now is.
  • A fact the plan relied on loses validity or confidence mid-task, for example because the user corrects it: the affected steps are re-planned before they run.

Nothing else re-plans. In particular, a worker cannot change a plan from the console: a worker who finds the script does not fit closes the step with the code that says why, and the trigger above does the rest.

3The classifier

Every step gets exactly one class, one reversibility and one route, and the rule that produces them is the same in every document of this publication. The three classes are ai (AI-runnable, executed by the harness on a surface without a person), human (human-runnable from a task card by a worker) and user (user-only, bounced to the user's own device as a one-tap approval or an act only the user can perform). The class says who executes; the reversibility and the envelope say how.

TestThe point-of-no-return test: "Can we return the world to its prior state by our own action, at no cost to the user and without a third party's consent? If not, the step is irreversible."

RuleIrreversible and outside the envelope: bounce to the user's device. Irreversible and inside it: dual control. Reversible and inside it: execute (ai or human per classifier). Anything outside the envelope that is reversible still cannot be executed by us; it becomes an extension request.

3.1Choosing between the three classes

A step is user in three cases, and the classifier checks them in this order. First, the act needs a factor only the user holds: an OTP, a biometric, a UPI PIN, a bank-app approval, a signature. {{otp}} is never an alias; OTPs are never ours. Second, the policy layer flags the step type as bounce or prohibited in the user's jurisdiction; a flag of bounce wins even when the user ticked the identity act in the envelope, and a flag of prohibited closes the step refused-policy before anyone attempts it. Third, the step is irreversible and outside the envelope.

Between ai and human the question is whether the step can be executed and verified without a person. A step is ai when its surface has a machine interface or the managed browser can complete it and the verification pass can confirm the expected outcome from the surface's state. A step is human when a person is needed on our side and no judgement is needed from that person: a phone conversation with a human on the far end, a form whose layout the harness cannot navigate reliably, a queue that needs a voice. The judgement stays in the plan; the worker gets a script.

The classifier is deterministic wherever it can be. A step-type catalogue per market carries each known step type's default class, its reversibility under the test, and its policy flag; the model proposes a step type, and the catalogue and the policy layer decide. A step type the catalogue does not know is treated as irreversible and outside the envelope, which means it bounces; that is the conservative default and it is what makes the catalogue grow, because every bounce of an unknown type is a request to add it.

4Execution surfaces

Every surface is ours, and a worker never touches a task with their own tools. That single rule is what makes the rest of this section possible: because the browser, the phone line and the mail relay are ours, we can put the substitution component at the edge of each one, mask what a worker sees, mute what a worker hears and capture evidence that has already been redacted. A real value exists on a surface only between the moment the substitution component places it and the moment the third party has consumed it. The site controls that keep a worker's own devices out of the room are operational and belong to the site controls in 04.

4.1The managed browser

The managed browser runs in our environment, on a browser sandbox we buy; the worker sees a video stream of it in the console and drives it by remote input. When a step reaches a field that needs a real value, the worker's card offers a Place control for the alias. Pressing it sends a request to the substitution component carrying the task id, the step id, the alias, the surface and a target descriptor (the DOM selector of the field). The substitution component checks the policy layer and the envelope, and then its own browser driver types the value into the field. The worker's stream renders that field as dots from the moment of placement: the stream renderer masks by coordinate at every substitution point, and by known-value matching against the vault's hashes everywhere else, so a confirmation page that echoes the value back is masked before the frame is encoded. The DOM capture that the evidence pipeline receives is masked the same way. The console never receives the value; it receives "placed" or a refusal code.

The masking fails closed. If the matcher cannot run, because the hash service is unreachable or a frame cannot be processed in time, the stream blanks and the step pauses with the surface held; the worker sees a blank panel and a reason, never an unmasked frame. Copy, download, print and screenshot are disabled in the console, and the stream is the only representation of the page that leaves the sandbox.

4.2Telephony

Calls run on our numbers and our call platform, with two legs: the worker's audio leg and the system leg. The dialler resolves the contactable party named in the envelope to a number we hold; a worker never types a number, and a party outside the envelope cannot be dialled. When the script reaches a value, the worker presses Place, and the substitution component speaks the value as synthesised speech or sends it as keypad tones on the call leg. For the duration of that placement window the worker's audio is muted in both directions and their panel shows "value placed"; the worker cannot hear the value and cannot speak over it. The window is recorded as a mute event that the evidence pipeline uses to silence the same span in the recording, and the transcriber replaces the value with its alias.

A third party can also say a value: a booking clerk reading a date of birth back, a bank agent reading an account number aloud. The worker's inbound audio therefore runs through a short delay buffer in which the live transcriber performs known-value matching against the vault's hashes and mutes the span in which a known value is spoken before it reaches the worker's ear. The far party hears nothing different; the call leg is unaffected. Each such mute is recorded as an event and appears in the ledger. The buffer's length is a pilot parameter and is set per market in the legal pack, not here. Scripts also instruct workers to decline readbacks, and a third party who insists on one is handled by the buffer, not by the worker's discretion.

4.3The mail relay

Outbound mail is composed with aliases, by a worker or by the harness, and sent from a per-task address that we own. The relay is a surface like the other two: at send time it asks the substitution component to replace each alias in the message with its value, the substitution component checks the envelope and the policy layer, performs the replacement in the outbound message inside its own boundary and writes the ledger entry, and the relay dispatches the result. The composed draft, which is what a worker sees, never contains a value. Inbound mail to a task address goes through the intake gateway like any other channel: it is tokenised at the edge by known-value matching and identifier pattern detection before it is attached to the task, and attachments follow the same path.

All three surfaces emit into the evidence pipeline (section 8), and all three refuse to operate for a step that is not in the running state, which is how the state machine, not the surface, decides whether anything happens at all.

5The state machine

A task cannot be forgotten, because forgetting has no transition. The task service holds every task in exactly one named state, gives every non-terminal state a live timer, records every change of state as an explicit event, and hands anything that has lost its timer to the watchdog. The invariant below is the contract; it appears identically on the worker console page because the console is the place where a person is most tempted to leave something for later.

A task never leaves the system by omission. Every task is in exactly one named state. Every non-terminal state carries a live timer. Every change of state is an explicit, recorded transition, and no task reaches a terminal state without one. Silence from the user is a legitimate way for a task to end: it moves through visible nudges into lapsed, and lapsed is not withdrawn. Silence from the system is forbidden: a task with no live timer is an exception, and the watchdog places it on the exceptions board until a person gives it one.

5.3Timers, nudges and the watchdog

Four kinds of timer exist and every live state carries one: the planning deadline, the step deadline, the nudge schedule and the third party's response window. All are per task type, set from a table that product owns; the defaults are illustrative until the pilot sets them, which is recorded as an open item in the open items in 07. The task service stores a timer as a scheduled event in the same append-only log as the transitions, so a timer and the transition it produces are one record apart and the watchdog can check both.

Nudges are recorded events on the timer of awaiting-authority, awaiting-user and awaiting-verdict, visible to the user and on the task's timeline. The illustrative default is three nudges over the schedule, then lapse. The lapse event records the state the task lapsed from, so a task abandoned before authorisation is never confused in measurement with a task completed but never judged. A lapsed task has no timer because it is terminal; revive is the only way out, and it re-enters planning rather than the state it left, because the world may have moved.

The watchdog runs on a fixed cycle and asks four questions of every record: does every live task have a future-dated timer; does every step in checking have a checker assigned and a check deadline; does every blocked-third-party step have a response window that has not yet passed; and has any nudge schedule been exhausted without a lapse event following it. Any failure places the task on the exceptions board, where it stays until a person gives it a timer, a checker or a transition. The watchdog's own heartbeat is an alarm in ordinary infrastructure monitoring, so a silent watchdog is itself an exception. The board and its operation are specified on the exceptions board on the worker console page and staffed per QA and escalation in 04.

5.4Step states and the event log

Steps have their own small machine: pending (in the plan, not ready), ready, running, checking (dual control; the other party is checking), bounced (a user step, with the user), closed (with an outcome code) and cancelled (withdrawn or superseded before running). A surface will only act for a step in running; a substitution request for a step in any other state is refused and logged. The task's state is a projection of its steps and its events: a task is active while any step is running or ready, awaiting-user while a step is bounced or a question is open, and so on. The projection is recomputed on every event, which is what prevents the task's state and its steps' states from drifting apart.

{
  "event_id": "e_000412",
  "task_id": "t_12",
  "at": "2026-09-02T15:12:40+05:30",
  "kind": "transition",
  "from": "active",
  "to": "awaiting-verdict",
  "transition": "report",
  "actor": { "kind": "system", "id": "task-service" },
  "reason": "all steps closed",
  "timer_set": { "kind": "nudge-schedule", "task_type": "IN/health/book-appointment" }
}

The event log is the audit trail, the input to the improvement loop and the source for the user's task timeline. It carries aliases and pseudonymous references only; the logging pipeline has no vault SDK, and any string in a log line that matches a known-value hash is rejected before it is written. Withdrawal is an ordinary event: steps in running are cancelled with the surface released, steps in checking are cancelled before they fire, and an irreversible step that has already fired is listed in the outcome report because a record of what was done is the only honest response to a withdrawal that came too late. A task whose validity window has expired cannot fire an irreversible step; the step becomes a request-extension and the task moves to awaiting-user until the user re-authorises. The design decision behind the whole machine is recorded in DR-005.

6The market adapter model

One core is built once and knows no country; each market is added as a repeatable unit of three parts. The core is the planner, the classifier, the task cards, the alias vault and substitution, the authority envelopes, the state machine, verification, the worker console, the access ledger and the intake gateway. The unit per country is a passport adapter, a legal pack and a shift. Expansion is the same playbook every time, and that is the point: the harness that keeps a worker in Bengaluru from seeing a value is the same harness in every market, so a new market never re-argues the trust design. The decision is DR-007; the playbook as a plan is in the expansion playbook in 06.

6.1The adapter interface

An adapter implements one interface, the same for every market, and tokenises inside its own boundary before anything leaves it. The interface has four operations: fetch a document (returns an alias for the document and non-sensitive metadata such as its type and issue date), fetch financial data under the user's consent (returns aliases for account identifiers and non-sensitive facts for the context store, such as the fact that an account exists at a named institution), manage a consent or mandate (create, inspect, revoke, always initiated by the user on their device), and present a document or identity attribute to a third party on a surface (routed through the substitution component like any other placement). The device bounce-back is not an adapter; it is universal, and every market uses the same one. Which rails each adapter wraps is the brief's fixed list, drawn in Figure 2.3; the current state of those rails, and what each permits a delegate to do, is researched in the passports in 03 and is not restated here.

6.2The legal pack and the shift

The legal pack holds three things the core reads at runtime and never hard-codes: the policy flag table for the jurisdiction, which is what the policy layer consults for every step; the data-residency map, which says which component's data lives where and under what safeguard, and which the vault's regional hosting is part of; and the refusal list for the market, which the planner consults before any step executes. The shift is the operational third: a market is not live until a shift covers its waking hours from the office, per the shift design in 04. The residency map itself is in the data-residency map in 03.

7Verification

Verification is the control loop, and it runs before "done" is ever shown to the user: every step closes with exactly one outcome code from a fixed vocabulary and the structured fields that code requires. The test a step is closed against is the expected outcome written on the step record before execution, so the executor never gets to decide what success meant after the fact. Artefacts attach to the outcome for audit and dispute only. Outcome codes are not ground truth of quality; the user's verdict is, and the verdict is the improvement loop specified in the verdict system in 01 and split from the control loop by DR-002. The full code vocabulary is the table on the worker console page; this section specifies the mechanics around it.

7.1Closing a step

An ai step is closed by the harness, which compares the surface's state after execution with the expected outcome: a confirmation page whose masked capture matches the expected pattern, a reference number in the expected form, a calendar entry that now exists. A human step is closed by the worker's structured result on the task card, which the console will not submit until the required fields for the chosen code are present. A user step is closed by the device's signed response. In every case the outcome record names the closing party, and for a dual-controlled step the checking party as well.

{
  "step_id": "s_03",
  "code": "ok-with-variance",
  "closed_by": { "kind": "worker", "id": "w_0x", "tier": "L1" },
  "checked_by": null,
  "fields": {
    "reference": "as given by the booking line",
    "timestamp": "2026-09-02T15:12:40+05:30",
    "party": "Max Healthcare booking line",
    "variance": "The earliest slot is the week after; a fee applies"
  },
  "artefacts": ["ev_...", "ev_..."],
  "closed_at": "2026-09-02T15:12:52+05:30"
}

The code chosen has consequences the task service applies automatically. blocked-needs-user creates a user step; blocked-outside-envelope creates an extension request or a user step; blocked-third-party starts a response window and moves the task to awaiting-third-party; failed-retryable re-queues the step on the same route; failed-final triggers re-planning; refused-policy records the policy reference and re-plans or bounces. A worker never chooses what happens next; the code does.

7.2Dual control

An irreversible step inside the envelope fires only after the other party has checked it. The executing party prepares the act and the step moves to checking with a check deadline. The checker receives the act in one sentence, the envelope lines it touches, the expected outcome and the prepared evidence, masked. The checker approves or declines; a checker cannot edit. On approval the step fires and the outcome record carries both identities; on decline the step returns to ready with the checker's reason, or re-plans if the reason says the route is wrong. When the AI executes, a worker checks; when a worker executes, the AI checks, in a separate model call that receives the envelope and the act and no conversation history. The checker is never the executor and never a worker who prepared any part of the step. A step in checking whose envelope is narrowed is re-checked against the narrowed envelope before it fires, and a check that passes its deadline goes to the exceptions board. The worker's view of all this is on the worker console page; the decision is DR-004.

7.3The envelope record and the ledger entry

The envelope is a versioned record. Every edit produces a new version with the user's device signature; steps carry the version they were classified against, so a step whose version is older than the current envelope is re-classified before it runs.

  "envelope_id": "env_12",

  "spend_cap": { "currency": "INR", "amount": 0 },

  "committable_acts": ["schedule", "cancel"],

8The evidence pipeline

No raw artefact is ever human-viewable, and the pipeline that guarantees it is part of the harness, not a later clean-up. Every surface emits screenshots, DOM captures, recordings, transcripts and call metadata into a pipeline with four stages: capture, redact, verify, store. Raw artefacts exist only in the pipeline's memory. A person may view an artefact only after the verify stage has passed it, and even then only for audit or dispute, with the viewing itself logged. The evidence system is a leak path in its own right, which is why the threat model in 03 treats it as one; the decision is DR-009, and the redaction methods are specified in artefact redaction in 03.

8.1The four stages

Capture takes the raw artefact from the surface together with the placement events the substitution component emitted for that step: the coordinates of every field it typed into, the time span of every audio placement, the aliases involved. Redact applies four methods: coordinate masking at every substitution point in a frame or DOM capture, audio muting over every placement window and every delay-buffer mute in a recording, alias replacement in every transcript, and known-value matching against the vault's hashes across the whole artefact to catch echoes the placement events did not predict. Verify is a second, independent pass, built and run separately from redact, that scans the redacted artefact for any known value and fails closed: an artefact in which a known value is detected is quarantined in memory, an incident is opened, and nothing is stored. Store writes the masked artefact with its step reference, its redaction manifest and a hash, and the artefact is from then on viewable for audit and dispute by a person whose viewing is itself a ledger event.

Two properties make the pipeline trustworthy rather than merely careful. Redact and verify share no code, so a defect in one does not hide in the other. And the pipeline holds no vault SDK: it receives the hashes it matches against, never the values, so a compromise of the pipeline yields masks and hashes, not data. Retention periods are per market and belong to the legal pack.

9The context store

The context store is what lets the planner act without asking the user things the user has already told us, and its design rule is that every fact says where it came from and how much to trust it. It is a temporal knowledge graph in which nodes are the user, institutions, documents, people and places, and edges are facts with validity intervals. The pattern the brief fixes is a Graphiti-style temporal graph; the library choice is a build decision recorded in DR-016. Sensitive fields live in the vault: the store holds the alias, never the value, and a fact about a PAN is a fact about {{pan}}.

9.1The fact schema

{
  "fact_id": "f_0281",
  "subject": "u_4471",
  "predicate": "has-account-at",
  "object": "HDFC Bank",
  "value_alias": "{{account.hdfc}}",
  "source": { "kind": "task-outcome", "ref": "t_09/s_05" },
  "observed_at": "2026-08-20",
  "confidence": "high",
  "user_confirmed": true,
  "confirmed_at": "2026-08-21",
  "valid_from": "2026-08-20",
  "valid_to": null,
  "superseded_by": null
}

Source is one of four kinds: a task outcome (the fact was established by a step that closed ok), the onboarding interview, a read-only connector the user chose, or a user statement in conversation. Confidence is assigned by the source kind and the fact's age, on a scale product owns, and it is qualitative in this publication: a user statement or a passport adapter result is high; a fact inferred from an outcome is medium until confirmed; a connector's fact carries the connector's confidence. User-confirmed is a separate flag, because a fact can be high-confidence and unconfirmed, and the planner treats them differently: a fact used in an irreversible step must be user-confirmed or come from a passport adapter, and a fact used to fill a form the user will see before it is submitted may be merely high-confidence.

9.2The temporal graph

Every fact has a validity interval, and a query is always made at a point in time: the planner asks what is true now, the audit asks what we believed when a step ran. A new fact that contradicts an existing one does not overwrite it; it opens with its own interval, the old fact's valid_to is set when the contradiction is resolved, and until then both are visible with a data-quality flag. That flag is what makes data-quality problems visible rather than silently wrong: a flagged fact cannot be used by a step; the planner turns the conflict into a question to the user at the next natural point, or into a blocked-needs-user step if a running task depends on it. A fact past its valid_to is never used. Facts are learned mostly as a by-product of doing tasks; every ok outcome carries a list of facts the step established, and the task service writes them with the step as their source. The onboarding interview and read-only connectors top the store up, per onboarding in 01.

9.3Who reads it

The planner reads the store, subject to the confidence rules above. A task card receives only the non-sensitive facts its step needs, as plain statements ("prefers morning appointments"), and only aliases for anything sensitive; a worker never queries the store. The user reads their own store as a profile in which every fact shows its source and date and can be confirmed, corrected or deleted from their device; a correction is a new fact with the user as its source, and it re-plans any open task that relied on the old one. Nothing else reads it. The store's non-sensitive contents sit with us, in the region the residency map assigns; its sensitive contents are aliases whose values sit in the vault's regional instance.

10The intake gateway

Every channel arrives at one door and leaves it as one format, already tokenised. The gateway accepts WhatsApp, the native app, SMS and iMessage, and the web, in text, voice and attachments, and produces the internal request record that every other component understands. Which channel is the front door in a given market is a launch choice, held amber and stated with its trigger in intake in 01 and recorded in DR-001; the gateway is the fixed decision underneath it, and nothing downstream knows or cares which channel a request came from.

10.1Tokenisation at the edge

The gateway is the first of the three ways a real value enters our boundary, and it tokenises before any other component, model or person sees the request. Three detectors run on every message: identifier pattern detection for the value types each market knows (a PAN's form, an Aadhaar number's form, a card number's check digit, a National Insurance number's form), known-value matching against the vault's hashes for values the user has given us before, and user declaration, where the user marks a value as sensitive or answers a structured prompt. Each detected value is sent to the vault, which returns an alias; the message that leaves the gateway carries the alias in the value's place. Attachments are tokenised whole: the document image goes to the vault, and the request carries an alias, the document type and the non-sensitive metadata the planner needs. Voice is transcribed inside the gateway's boundary, and the transcript is tokenised the same way before the audio is handed to the evidence pipeline. A value the detectors miss is the residual risk of this component; the known-value matching on every surface and in the evidence pipeline is the second line, and the threat model in 03 names the path.

Two rules follow from the format. The bounce channel is the device binding, never the channel the request came from: a one-tap approval on a chat thread would be an approval anyone holding the phone number could give, so bounces and envelope prompts go to the authenticated device and the chat thread receives only the notification that something is waiting. And a message that references an existing task routes to it: the gateway resolves thread_ref by explicit reply, by a task reference in the text, or by the planner's judgement when neither is present, and the task service applies resume or revive accordingly. Refusals are not the gateway's job; a request the planner finds to be outside what we do is refused in received or planning against the list in what we refuse to do in 01, and the user is told why.
