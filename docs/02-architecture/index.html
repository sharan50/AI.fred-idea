1Overview

The harness is a control system wrapped around a planner, not a chat model with tools attached. A request enters through one gateway, becomes a plan of classified steps, and each step executes on a surface we own, closes with a code from a fixed vocabulary and leaves behind a redacted artefact. Real values exist inside our boundary in two places only: the substitution component, and the surface field, call leg or outbound message it has just placed into, for as long as the third party takes to consume it. Every task sits in one named state with a live timer until a recorded transition ends it. Those sentences are the architecture; the rest of this page is their consequences.

Vocabulary: a task is one user request from intake to a terminal state; a step is the unit of execution and classification; a worker is a person on our side who executes a step from a task card; the user is the customer who delegated it. The worker console specifies what a worker sees; the alias model in 03 and the threat model in 03 specify and close the trust mechanics this page enforces.

Each component has one responsibility, and the boundaries between them are where the guarantees live; sections 2 to 10 specify them. Two straddle the boundary and get a word here. The policy layer's mechanism is core but its table is the policy flag table in 03. The user's device is outside: it is where every user step lands, where the envelope is confirmed and edited, and where the access ledger in 03 and the verdict live.

Three boundaries carry the guarantees. Our trust boundary encloses every component that handles aliases; the vault SDK is absent from the model runtime, the worker console and the logging pipeline, so nothing inside can detokenise except the substitution component. The user's device is where authority originates and where irreversible acts outside the envelope are performed by the user, never by us. The vault sits outside because a tokenisation service is a bought commodity (DR-008) whose regional hosting is part of the residency answer, and because a boundary we do not operate is one our staff cannot cross. The build order is the build sequence in 06; the build-versus-buy line is the build-versus-buy table in 06.

2The planner

A plan and an envelope proposal are the planner's output, and its contract is that neither contains a real value. Its inputs are the normalised request, the context-store facts that bear on it (each with confidence and validity), the step templates from the taxonomy in 01, the flag table for the user's market and, when re-planning, the task's envelope and closed steps. The planner is a model with a schema-validated output, and the harness rejects a plan that fails validation. The model runtime has no vault SDK and the request reaches it already tokenised, so the planner cannot leak what it never held.

2.1Input and output

A plan is an ordered list of steps, each carrying a one-sentence purpose, a proposed class, the surface, the party, the act type, the fields it needs as aliases, an expected outcome written as a testable statement, a deadline and a reversibility hint. The planner proposes; the classifier stamps the authoritative class, reversibility and route. The envelope proposal is sized to the plan: the smallest spend cap, party list, act lists and validity window that let it complete, with any excess over the user's standing preferences marked. The plain-words plan summary goes to the user's device with the envelope, and no step executes before the user authorises them.

{
  "plan_id": "p_12.1",
  "task_id": "t_12",
  "summary": "Book the earliest cardiology appointment next week
              with Max Healthcare, then add it to your calendar.",
  "steps": ["s_01", "s_02", "s_03", "s_04"],
  "envelope_proposal": "env_12/v1",
  "facts_used": [
    { "fact": "f_0281", "confidence": "high", "user_confirmed": true }
  ],
  "produced_at": "2026-09-02T14:31:40+05:30",
  "supersedes": null
}

Every plan records the facts it relied on and their confidence at the time, so when a fact later changes the task service can find every open plan that depended on it.

2.2Re-planning triggers

Re-planning is a recorded event, never a silent edit, and it never touches a step that has already fired. A step the new plan no longer needs closes superseded; a step in flight is allowed to close first. The triggers are fixed:

  • A step closes failed-final: the route is exhausted and the planner finds another, or reports that none exists.
  • A blocked-third-party response window expires: the task service re-plans on the tick; a new route applies escalate-resume, and no route sets a holding window and puts the task on the exceptions board (section 5.3).
  • The user extends the envelope: classification re-runs for every affected step, because a step that was outside may now be inside.
  • The user narrows it: every step not yet fired is re-checked, and a step now outside becomes an extension request or a user step.
  • A blocked-needs-user step resolves with a new fact: the steps that depended on the gap are re-classified.
  • The verdict is wrong-outcome: the parent closes with that verdict and a linked child task opens in planning with the parent's trace attached.
  • A lapsed task is revived by a user message: it re-enters planning so that stale steps are re-checked against the world as it now is.
  • A fact the plan relied on loses validity or confidence mid-task: the affected steps are re-planned before they run.

Nothing else re-plans. In particular, a worker cannot change a plan from the console: a worker who finds the script does not fit closes the step failed-final with the reason "script does not fit" and the alternatives-tried checklist, or blocked-needs-user where the gap is a fact only the user holds, and the triggers above do the rest.

3The classifier

Every step gets exactly one class, one reversibility and one route, by a rule that is the same in every document of this publication. The classes are ai (executed by the harness on a surface, without a person), human (executed by a worker from a task card) and user (bounced to the user's own device). The class says who executes; the reversibility and the envelope say how.

TestThe point-of-no-return test: "Can we return the world to its prior state by our own action, at no cost to the user and without a third party's consent? If not, the step is irreversible."

RuleIrreversible and outside the envelope: bounce to the user's device. Irreversible and inside it: dual control. Reversible and inside it: execute (ai or human per classifier). Anything outside the envelope that is reversible still cannot be executed by us; it becomes an extension request.

As a lookup, two questions give four routes, and none has us executing outside the envelope:

Reversible and inside: execute
ai or human, per the classifier.
Reversible and outside: extension-request
Nobody, until the user extends the envelope from their device.
Irreversible and inside: dual-control
ai or human executes; the other party checks before it fires.
Irreversible and outside: bounce
The user, on their own device, in one of the two forms in section 3.1.

3.1Choosing between the three classes

A step is user in three cases, checked in this order. First, the act needs a factor only the user holds: an OTP, a biometric, a UPI PIN, a bank-app approval, a signature; {{otp}} is never an alias, because OTPs are never ours. Second, the policy flag table in 03 marks the step type bounce or prohibited in the user's jurisdiction; bounce wins even when the user ticked the identity act, and prohibited closes the step refused-policy before anyone attempts it. Third, the step is irreversible and outside the envelope.

Between ai and human the question is whether the step can be executed and verified without a person. A step is ai when a machine interface or the managed browser can complete it and the verification pass can confirm the expected outcome from the surface's state. A step is human when a person is needed on our side but no judgement is: a conversation with a human on the far end, a form the harness cannot navigate reliably, a queue that needs a voice. The judgement stays in the plan; the worker gets a script.

A bounced irreversible step takes one of two forms, and the step-type catalogue records which. In the first the user performs the act on their own device, through a rail or an app, and we record only the device's signed outcome. In the second the user's one tap is a device-signed envelope extension scoped to that step: it produces a new envelope version, the step is re-classified as inside the envelope and fires under dual control, and the ledger line names the version it fired under. Nothing we perform runs on the tap alone.

The classifier is deterministic wherever it can be. The step-type catalogue's schema is core; its entries per market ship in the legal pack (section 6.2) and carry each step type's default class, reversibility, policy flag, bounce form, allowed response windows, delay-buffer length and allowed browser origins. The model proposes a step type; the catalogue and the policy layer decide. An unknown step type counts as irreversible and outside the envelope, so it bounces in the first form; that conservative default is also how the catalogue grows.

The record carries aliases, a pseudonymous task reference and nothing that identifies the user. The task card is a projection of it: the card shows the fields the step needs and no others because the record lists no others. approval_token is null for a reversible step; for a dual-controlled step it holds the check id, the envelope version and the expiry of section 7.2.

The user's name and contact details are vault-held aliases like any other: {{name}}, {{phone}}, {{email}} and {{address}}. A booking line needs a patient's name, so the step carries {{name}}, the substitution component places it, the delay buffer in section 4.2 mutes its readback, and the worker never learns it. This adds four aliases to the list in the alias model in 03.

4Execution surfaces

We own every surface, and a worker never touches a task with their own tools. Because the browser, the phone line and the mail relay are ours, the substitution component (isolated as specified in the substitution component in 03) sits at the edge of each, what a worker sees is masked, what a worker hears is muted, and the evidence is redacted before it leaves. A real value exists on a surface only between placement and the third party's consumption of it. The site controls that keep a worker's own devices out of the room are the site controls in 04.

4.1The managed browser

The managed browser runs in our environment on a browser sandbox we buy; the worker sees a video stream of it and drives it by remote input. Navigation is allow-listed to the origins the step-type catalogue records for the envelope's contactable parties; anything else is blocked and logged. When a step reaches a field that needs a real value, the card offers a Place control for the alias. Pressing it sends the substitution component the task id, the step id, the alias, the surface and a target descriptor: the page origin and the DOM selector of the field. The substitution component checks the policy layer and the envelope, refuses with a code and a ledger line any placement whose origin does not resolve to a contactable party, and otherwise types the value into the field with its own browser driver. The console receives "placed" or a refusal code, never the value.

Masking runs on the DOM text and the accessibility tree, never on pixels. The stream renderer masks by coordinate at every substitution point; everywhere else it runs known-value matching against the vault's hashes and the gateway's identifier-pattern detectors over the page text, maps each match to its layout box and paints the box as dots before the frame is encoded; image and canvas regions are masked whole unless a per-site mask map clears them. That covers a form and a confirmation page. It does not cover an authenticated portal, which shows balances, history, other account numbers, names and addresses that were never vaulted, so a step on such a portal is classified ai, with no stream to a person, unless the catalogue carries a per-site mask map for it. The residual is a value in no known form on a page no mask map covers; the threat model in 03 names the path. The DOM capture the evidence pipeline receives is masked the same way.

The masking fails closed: if the matcher cannot run, because the hash service is unreachable or a frame cannot be processed in time, the stream blanks and the step pauses with the surface held, and the worker sees a reason, never an unmasked frame. Copy, download, print and screenshot are disabled in the console, and the stream is the only representation of the page that leaves the sandbox.

4.2Telephony

Calls run on our numbers and our call platform, with two legs: the worker's audio leg and the system leg. The dialler resolves the contactable party named in the envelope to a number we hold; a worker never types a number, and a party outside the envelope cannot be dialled. When the script reaches a value the worker presses Place, and the substitution component speaks it as synthesised speech or sends it as keypad tones on the call leg, with the worker's audio muted in both directions and their panel showing "value placed". The window is recorded as a mute event; the evidence pipeline silences the same span in the recording, and the transcriber replaces the value with its alias.

A third party can also say a value: a clerk reading a name or a date of birth back, a bank agent reading an account number aloud, a policy number issued on the call. The worker's inbound audio therefore runs through a short delay buffer in which the live transcriber runs known-value matching against the vault's hashes and the identifier-pattern detectors, and mutes the span in which a match is spoken before it reaches the worker's ear. The far party hears nothing different, and each mute is a recorded event in the ledger. The inbound leg fails closed: when the matcher cannot keep pace with the buffer or cannot reach the hashes, the worker's inbound audio mutes, the call panel shows the reason until the matcher catches up, and the mute is recorded. The buffer's length is a pilot parameter and ships per market in the catalogue entries of the legal pack. Scripts instruct workers to decline readbacks and to ask a party issuing a new identifier to send it by the mail relay or to the user directly; the residual is an identifier in no known form, heard once by a worker, and the threat model in 03 carries the path.

4.3The mail relay

Outbound mail is composed with aliases, by a worker or by the harness, and sent from a per-task address we own. At send time the relay asks the substitution component to replace each alias with its value; the substitution component checks the envelope and the policy layer, performs the replacement inside its own boundary and writes the ledger entry; the relay dispatches the result, holds it only until the receiving server accepts it and keeps no sent copy. The evidence copy is the alias draft plus the delivery receipt, and the draft a worker sees never contains a value. Inbound mail to a task address, attachments included, goes through the intake gateway like any other channel and is tokenised at the edge.

All three surfaces emit into the evidence pipeline (section 8), and all three refuse to operate for a step not in running: the state machine, not the surface, decides whether anything happens at all.

5The state machine

A task cannot be forgotten, because forgetting has no transition. The task service holds every task in exactly one named state, gives every non-terminal state a live timer, records every change of state as an explicit event and hands anything that has lost its timer to the watchdog. The invariant below is the contract; it appears identically on the worker console page, where a person is most tempted to leave something for later.

A task never leaves the system by omission. Every task is in exactly one named state. Every non-terminal state carries a live timer. Every change of state is an explicit, recorded transition, and no task reaches a terminal state without one. Silence from the user is a legitimate way for a task to end: it moves through visible nudges into lapsed, and lapsed is not withdrawn. Silence from the system is forbidden: a task with no live timer is an exception, and the watchdog places it on the exceptions board until a person gives it one.

5.3Timers, nudges and the watchdog

Four kinds of timer exist and every live state carries one: the planning deadline, the step deadline, the nudge schedule and the third party's response window. All are per task type, set from a table product owns, and the defaults are illustrative until the pilot sets them. A timer is a scheduled event in the same append-only log as the transitions, so a timer and the transition it produces are one record apart and the watchdog can check both.

Expiry is acted on by the system, on the tick, never by a person. Nudges are recorded events on the timer of awaiting-authority, awaiting-user and awaiting-verdict, visible to the user and on the task's timeline; the illustrative default is three nudges, after which the task service writes the lapse event itself, recording the state lapsed from, so a task abandoned before authorisation is never confused in measurement with one completed but never judged. For awaiting-verdict the schedule runs from the recorded delivery of the outcome report, which the task service checks; no person confirms anything before a lapse. When a response window expires the task service re-plans: a new route applies escalate-resume; no route sets a holding window, a recorded timer event named extend-window, and places the task on the exceptions board for a person to chase the party. A lapsed task is terminal and has no timer; revive is the only way out, into planning rather than the state it left, because the world may have moved.

The watchdog runs on a fixed cycle and asks four questions of every record: does every live task have a future-dated timer; does every step in checking have a checker and a check deadline not yet passed; has any response window expired without resume, escalate-resume or extend-window following within one cycle; and has any nudge schedule been exhausted without a lapse event within one cycle. The last two are defects in the task service, not routine work. Any failure places the task on the exceptions board until a person gives it a timer, a checker or a transition. The watchdog's own heartbeat is an alarm in ordinary monitoring, so a silent watchdog is itself an exception. The board is specified on the exceptions board on the worker console page and staffed per QA and escalation in 04.

5.4Step states and the event log

Steps have their own small machine: pending (in the plan, not ready), ready, running, checking (dual control; the other party is checking), bounced (a user step, with the user), closed (with an outcome code) and cancelled (withdrawn or superseded before running). A surface acts only for a step in running; a substitution request for any other state is refused and logged. The task's state is a projection of its steps and events, with a fixed precedence: any step ready, running or checking makes the task active, timed by the earliest step deadline; otherwise any step bounced, or an open question or extension request, makes it awaiting-user on the nudge schedule; otherwise any step closed blocked-third-party makes it awaiting-third-party on that step's response window; and when every step is closed or cancelled, report moves it to awaiting-verdict. The projection is recomputed on every event, so the task's state and its steps' states cannot drift apart.

  "task_id": "t_12",
  "at": "2026-09-02T15:12:40+05:30",
  "kind": "transition",
  "from": "active",
  "to": "awaiting-verdict",

The event log is the audit trail, the input to the improvement loop and the source for the user's task timeline. It carries aliases and pseudonymous references only; the logging pipeline has no vault SDK, and a log line matching a known-value hash is rejected before it is written. Withdrawal is an ordinary event: steps in running are cancelled with the surface released, steps in checking are cancelled before they fire and every approval token is voided, and an irreversible step that has already fired is listed in the outcome report, the only honest response to a withdrawal that came too late. Expiry of the validity window stops every step not yet fired, reversible or not: the task moves to awaiting-user with a request-extension, and no surface acts for a step whose envelope version has expired. The decision behind the machine is DR-005.

6The market adapter model

One core is built once and knows no country; each market is added as a repeatable unit of three parts. The core is the planner, the classifier, the task cards, the alias vault and substitution, the authority envelopes, the state machine, verification, the worker console, the access ledger, the intake gateway and the policy layer's mechanism; the flag table that mechanism reads is the per-market half. The unit per country is a passport adapter, a legal pack and a shift. The harness that keeps a worker in Bengaluru from seeing a value is the same harness everywhere, so a new market never re-argues the trust design. The decision is DR-007; the playbook is the expansion playbook in 06.

6.1The adapter interface

An adapter implements one interface, the same for every market, and tokenises inside its own boundary before anything leaves it. Four operations: fetch a document (returns an alias and non-sensitive metadata such as type and issue date); fetch financial data under the user's consent (returns aliases for account identifiers and non-sensitive facts for the context store); manage a consent or mandate (create, inspect, revoke, always initiated by the user on their device); and present a document or identity attribute to a third party on a surface, through the substitution component like any other placement. The device bounce-back is not an adapter; it is universal. The rails each adapter wraps are the brief's fixed list, drawn in Figure 2.3; what each permits a delegate to do is researched in the passports in 03.

6.2The legal pack and the shift

The legal pack holds four things the core reads at runtime and never hard-codes: the policy flag table, which the policy layer consults for every step; the data-residency map, which says which component's data lives where and under what safeguard, the vault's regional hosting included; the refusal list, which the planner consults before any step executes; and the step-type catalogue's entries for the market (section 3.1), whose schema is core and whose values per step type are the default class, reversibility, policy flag, bounce form, allowed response windows, delay-buffer length and allowed origins. The shift is the operational third: a market is not live until a shift covers its waking hours from the office, per the shift design in 04. The residency map itself is the data-residency map in 03.

7Verification

Verification is the control loop, and it runs before "done" is ever shown to the user: every step closes with exactly one outcome code from a fixed vocabulary and the structured fields that code requires. The test is the expected outcome written on the step record before execution, so the executor never decides after the fact what success meant. Artefacts attach for audit and dispute only. Outcome codes are not ground truth of quality; the user's verdict is, the improvement loop in the verdict system in 01, split from the control loop by DR-002. The vocabulary is the table on the worker console page; this section specifies the mechanics around it.

7.1Closing a step

An ai step is closed by the harness, which compares the surface's state after execution with the expected outcome: a masked capture matching the expected pattern, a reference in the expected form, a calendar entry that now exists. A human step is closed by the worker's structured result on the task card, which the console will not submit until the required fields are present. A user step is closed by the device's signed response. The outcome record names the closing party and, for a dual-controlled step, the checking party.

{
  "step_id": "s_03",
  "code": "ok-with-variance",
  "closed_by": { "kind": "worker", "id": "w_0x", "tier": "L1" },
  "checked_by": null,
  "fields": {
    "reference": "as given by the booking line",
    "timestamp": "2026-09-02T15:12:40+05:30",
    "party": "Max Healthcare booking line",

  "artefacts": ["ev_...", "ev_..."],

A variance is never an envelope line: anything that would breach one, a fee against this task's spend cap of zero included, closes blocked-outside-envelope with the line it would breach, regardless of how small. The code chosen has consequences the task service applies and a worker never chooses: blocked-needs-user creates a user step; blocked-outside-envelope an extension request or a user step; blocked-third-party a response window and awaiting-third-party; failed-retryable a re-queue on the same route; failed-final a re-plan; refused-policy a policy reference and a re-plan or a bounce.

7.2Dual control

Nothing irreversible inside the envelope fires until the other party has checked it. The executing party prepares the act and the step moves to checking with a check deadline. The checker receives the act in one sentence, the envelope lines it touches, the expected outcome and the prepared evidence, masked, and approves or declines; a checker cannot edit. On approval the step returns to running with an approval token bound to the check id, the envelope version the check was made against and an expiry equal to the step deadline; a surface refuses to fire an irreversible act without a token naming the current envelope version, so an approval never outlives its check. An envelope edit voids every outstanding token and returns the step to checking, and a step already in checking is re-checked against the new version; a withdrawal voids the tokens and cancels the step. The outcome record carries both identities. On decline the step returns to ready with the checker's reason, or re-plans if the reason says the route is wrong. When the AI executes, a worker checks; when a worker executes, the AI checks, in a separate model call that receives the envelope and the act and no conversation history. The checker is never the executor and never a worker who prepared any part of the step; a check that passes its deadline goes to the exceptions board. The worker's view is on the worker console page; the decision is DR-004.

7.3The envelope record and the ledger entry

The envelope is a versioned record; the user's view of it is the envelope in 01. The proposal is version 1; authorisation and every later edit produce a new version with the user's device signature, and steps carry the version they were classified against, so a step whose version is older than the current envelope is re-classified before it runs.

8The evidence pipeline

No raw artefact is ever human-viewable, and the pipeline that guarantees it is part of the harness, not a later clean-up. Every surface emits screenshots, DOM captures, recordings, transcripts and call metadata into four stages: capture, redact, verify, store. Raw artefacts exist only in the pipeline's memory; a person may view an artefact only after verify has passed it, only for audit or dispute, with the viewing logged. The evidence system is a leak path in its own right, and the threat model in 03 treats it as one; the decision is DR-009, the methods are in artefact redaction in 03.

8.1The four stages

Capture takes the raw artefact from the surface together with the placement events the substitution component emitted for the step: the coordinates of every field it typed into, the time span of every audio placement, the aliases involved. Redact applies four methods: coordinate masking at every substitution point in a frame or DOM capture, audio muting over every placement window and delay-buffer mute, alias replacement in every transcript, and known-value matching against the vault's hashes across the whole artefact to catch echoes the placement events did not predict. Verify is a second, independent pass that scans the redacted artefact for any known value and fails closed: a detection quarantines the artefact in memory, opens an incident and stores nothing. Store writes the masked artefact with its step reference, its redaction manifest and a hash, after which it is viewable for audit and dispute by a person whose viewing is itself a ledger event.

Redact and verify share no code, so a defect in one does not hide in the other, and the pipeline holds no vault SDK: it receives the hashes it matches against, never the values, so a compromise of the pipeline yields masks and hashes, not data. Retention periods are per market and belong to the legal pack.

9The context store

The context store lets the planner act without asking the user things they have already told us, and its design rule is that every fact says where it came from and how much to trust it. It is a temporal knowledge graph: nodes are the user, institutions, documents, people and places; edges are facts with validity intervals. The brief fixes a Graphiti-style temporal graph; the library choice is recorded in DR-016. Sensitive fields live in the vault: the store holds the alias, never the value, and a fact about a PAN is a fact about {{pan}}.

source.kind is one of five: task-outcome (established by a step that closed ok), onboarding, connector (a read-only connector the user chose), user-statement and passport-adapter. Confidence follows the source kind and the fact's age, on a scale product owns and qualitative here: a user statement or a passport adapter result is high; a fact inferred from an outcome is medium until confirmed; a connector's fact carries the connector's confidence. User-confirmed is a separate flag, because a fact can be high-confidence and unconfirmed: a fact used in an irreversible step must be user-confirmed or come from a passport adapter; a fact used to fill a form the user will see before submission may be merely high-confidence.

9.2The temporal graph

Every fact has a validity interval, and a query is always made at a point in time: the planner asks what is true now, the audit asks what we believed when a step ran. A new fact that contradicts an existing one does not overwrite it; it opens with its own interval, the old fact's valid_to is set when the contradiction is resolved, and until then both carry a data-quality flag. A flagged fact cannot be used by a step: the planner turns the conflict into a question to the user at the next natural point, or into a blocked-needs-user step if a running task depends on it. A fact past its valid_to is never used. Facts are learned mostly by doing tasks: every ok outcome carries the facts the step established, written with the step as their source; the onboarding interview and read-only connectors top the store up, per onboarding in 01.

9.3Who reads it

The planner reads the store under the confidence rules above. The user reads their own store as a profile in which every fact shows its source and date and can be confirmed, corrected or deleted from their device; a correction is a new fact with the user as its source, and it re-plans any open task that relied on the old one. Nothing else reads it, and its non-sensitive contents sit in the region the residency map assigns.

10The intake gateway

Every channel arrives at one door and leaves it as one format, already tokenised. The gateway accepts WhatsApp, the native app, SMS and iMessage, and the web, in text, voice and attachments, and produces the internal request record every other component understands. Which channel is the front door in a market is a launch choice, held amber with its trigger in intake in 01 and recorded in DR-001; the gateway is the fixed decision underneath, and nothing downstream knows which channel a request came from.

10.1Tokenisation at the edge

The gateway is the first of the three ways a real value enters our boundary, and it tokenises before any other component, model or person sees the request. Three detectors run on every message: identifier-pattern detection for the value types each market knows (a PAN's form, an Aadhaar number's form, a card number's check digit, a National Insurance number's form), known-value matching against the vault's hashes, and user declaration, where the user marks a value as sensitive or answers a structured prompt. Each detected value goes to the vault, and the alias it returns takes its place. Attachments are tokenised whole: the document image goes to the vault, and the request carries an alias, the document type and the metadata the planner needs. Voice is transcribed inside the gateway's boundary and the transcript tokenised the same way; the audio goes to the evidence pipeline with the time span of every detected value, the pipeline mutes those spans, and verify checks the transcript of the redacted audio for known values. A value the detectors miss is this component's residual risk; the known-value matching on every surface and in the evidence pipeline is the second line, and the threat model in 03 names the path.

Two rules follow from the format. The bounce channel is the device binding, never the channel the request came from: a one-tap approval on a chat thread would be an approval anyone holding the phone number could give, so bounces and envelope prompts go to the authenticated device, and the chat thread receives only a notification that something is waiting. A message that references an existing task routes to it: the gateway resolves thread_ref by explicit reply, by a task reference in the text or by the planner's judgement, and the task service applies resume or revive.
